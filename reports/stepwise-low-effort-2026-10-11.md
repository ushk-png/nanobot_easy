# 단계 호출 추론 강도 low 적용·Z3 기본 비활성 보고 (2026-10-11)

브랜치: `fix/stepwise-latency-empty-answer`, 커밋 `2cbebeec` (push 안 함). 세션 사례 파일 보관은 지시대로 보류했다.

## 1. 추론 강도 low

- `bridge.py :: STAGE_REASONING_EFFORT = "low"`. 단계·경로 판정(compose: direct/reuse/new)·검토 호출이 모두 `ProviderStageLLM`을 거치므로 같은 강도가 적용된다.
- **실제로 보낸 값 기록:**
  - `LLMResponse.request_options`를 추가했다. xAI provider는 `extraBody`까지 합친 최종 요청 본문의 `reasoning` 필드를 이 값으로 돌려준다.
  - 호출 기록에는 `reasoning_request`와 `reasoning_request_source`를 남긴다. provider가 보고한 값이면 source는 `request`, 보고하지 않아 effort로 계산한 값이면 `derived`다.
- **실측 확인:** 아래 재실행의 모든 호출(compose 4회, 단계 18회, 총 22회)이 `reasoning_request = {"summary": "concise", "effort": "low"}`, `source = "request"`였다.
- 사용자 안내 문구가 실행 강도를 밝히도록 바꿨다: "…가장 낮은 강도(low)로 켠 채 실행됩니다."
- 지니 설정의 `reasoningEffort: none`은 그대로다. 이 값이 단계별 경로를 켜는 조건으로 쓰인다.

## 2. 같은 시나리오 재실행 비교

이전 값은 effort 생략(= xAI 기본 high), 이후 값은 low다. 같은 요청·같은 설정으로 각 1회씩 실행했다.

| 시나리오 | 경로 | 결과 | 호출 (이전→이후) | 시간 (이전→이후) | 추론 토큰 (이전→이후) | 결론 (이전→이후) |
|---|---|---|---:|---:|---:|---|
| 잡담 | direct | 일반 루프로 넘김 | 1 → 1 | 3.9초 → 3.0초 | 227 → 145 | – |
| 보고서 선정 | reuse (method-evaluation) | 완료 → 완료 | 10 → **8** | 634초 → **89초** | 42,703 → **5,597** | C 선정 → C 선정 (`suitable`) |
| §13 평가 | reuse (method-evaluation) | 완료 → 완료 | 8 → 8 | 294초 → **81초** | 23,677 → **5,386** | 부적합 → 부적합 (`unsuitable`) |
| └ 후속 update | update | 완료 → 완료 | 5 → 5 (compose + S4~S7) | 229초 → **72초** | 17,949 → **4,469** | `unsuitable` → `unsuitable` |

- 보고서 선정은 이전에 S6이 결함을 한 번 지적해 S5·S6을 다시 실행했기 때문에 10회였다. 이번에는 다시 실행하지 않아 8회다.
- 수정 전 원래 기록(08:01 126초, 08:27 284초, 둘 다 빈 답변)과 비교하면, 보고서 선정이 89초에 답변까지 완료됐다.

### 결론 차이

- **보고서 선정:** 같다. 두 번 모두 C를 선정했고, A(감사 로그 없음)·B(도입비 초과)·D(감사 로그 미확인) 제외 이유도 같다. 이전 실행은 결론 상태를 기록하지 않았고, 이번은 `suitable`이다.
- **§13 평가:** 같다. "외부 API 방식은 내부망 필수 조건 미충족으로 부적합"이다.
- **후속 update:** 결론 상태(`unsuitable`)와 S4~S7만 다시 실행한 점은 같고, **답변 내용이 다르다.**
  - **교체된 사실:** 이전은 `f4`, 이번은 `f3`이다. 사실 번호는 실행마다 새로 매겨지므로 번호 자체는 비교 의미가 없다.
  - **이전 답변:** "확인된 필수조건이 미충족이라 부적합… 나머지 필수조건은 미확인"이었다.
  - **이번 답변:** "외부 API 방식은 내부망 필수 조건을 못 지켜 부적합… **내부망 대체 기능은 아직 확인되지 않았습니다**"다. 사용자가 "로컬 모델로도 돌릴 수 있다고 합니다"라고 알린 뒤인데도 대체 기능을 미확인으로 남겼다.
  - **원인은 미확인이다.** 후보는 두 가지다. 하나는 첫 호출이 전해 들은 말("~라고 합니다")을 `estimated`나 `unknown`으로 넣었을 가능성이다. 다른 하나는 교체 대상 사실이 "대체 기능 미확인" 사실이 아니었을 가능성이다. 실행 기록에 사실 목록과 판단 목록이 저장되지 않아 확인할 수 없었다. 기록에 넣으려면 실행 기록 형식을 바꿔야 한다.

## 3. Z3 기본 비활성

- **새 설정:** `agents.defaults.stepwiseZ3Check`(기본 `false`). 전달 경로는 `AgentLoop` → `run_reasoning_procedure(z3_check=…)` → `ReasoningEngine(z3_check=…)`이다.
- **꺼져 있을 때:** 규칙 판단 절차의 점검 단계에서 Z3를 실행하지 않는다. 대신 `z3:entailment` 검사를 `result = "DISABLED"`로 기록한다. 통과로 채우지 않는다(설계서 6.2). 기록의 한계 설명에 다시 켜는 설정 이름을 남긴다.
- **다시 켜기:** 지니 설정의 `agents.defaults`에 `"stepwiseZ3Check": true`를 넣는다. 켜면 기존 동작이 그대로 돈다.

## 4. S6 조건부 실행 — 제안 (구현하지 않음)

### 판단 근거: S6은 여전히 단일 단계 중 가장 비싸다

| 시나리오 | S6 시간 | 전체 단계 중 순위 | S6 추론 토큰 | 실행 시간 중 비중 |
|---|---:|---|---:|---:|
| 보고서 선정 | 17.2초 | 1위 (다음은 S4 15.4초) | 1,083 (S4 1,099와 비슷) | 19% |
| §13 평가 | 18.0초 | 1위 | 1,367 (1위) | 22% |
| 후속 update | 30.3초 | 1위 | 1,871 (1위) | 42% |

### 제안 구현안

1. **조건 판정.** 코드 함수 `_semantic_review_required(case)`가 S5 결과만 보고 판정한다. LLM은 쓰지 않는다. 아래 중 하나라도 해당하면 S6 모델 검토를 실행한다.
   - 결론이 참조한 판단(`conclusion.judgment_ids`) 중 `result == "unknown"`이 있다.
   - 그 판단의 근거 사실 중 `status`가 `estimated`나 `unknown`인 것이 있다.
   - 판단이나 사례에 `assumptions`가 있다.
   - `conclusion.status`가 `unsuitable` 또는 `conditionally_suitable`이다.
   - 이번 실행이 `update` 경로이고, 바뀐 사실에 의존하는 판단이 결론에 쓰였다.
2. **조건이 없을 때.** S6의 **코드 검사(code:S6)는 항상 실행**한다. 모델 호출은 하지 않고, `llm:S6` 검사를 `result = "SKIPPED"`로 기록한다. 이때 판정 근거(어떤 조건도 해당하지 않음)를 함께 남긴다.
   - 이렇게 생략하려면, 승인 절차의 S6 단계 계약(설계서 6.1 검사 목록)에 의미 검사를 "조건부 필수"로 명시해야 한다. 그래야 설계서 6.2의 "필수 의미 검사가 생략되면 정상 통과하지 못한다"와 충돌하지 않는다.
3. **적용 범위.** 승인 절차의 S6에만 적용한다. 구조화된 결론 객체가 없는 동적 절차의 점검 단계는 지금처럼 항상 실행한다.
4. **테스트.**
   - 조건별 실행·생략.
   - `SKIPPED`가 `passed`로 바뀌어 기록되지 않는지.
   - update 경로에서 바뀐 사실에 의존하는 결론은 항상 검토되는지.

### 예상 효과와 한계

- **이번 세 시나리오에서는 절감이 거의 없을 가능성이 높다.**
  - §13 평가와 후속 update는 결론이 `unsuitable`이라 그대로 실행된다.
  - 보고서 선정은 결론이 `suitable`이지만 판단 j1~j5를 모두 참조한다. 그중 D의 "감사 로그 미확인" 판단이 `unknown`일 가능성이 높아, 첫 번째 조건에 걸릴 것으로 보인다. 판단 목록은 기록에 없어 미확인이다.
- **절감이 생기는 경우:** 근거가 모두 확인된 `suitable` 결론이다. 이때 S6 모델 호출 1회(약 17~30초, 추론 1~2천 토큰)를 아낀다.
- **함께 검토할 대안:** S6 입력을 결론과 그것이 참조한 판단·사실로 줄이는 방법이다. 설계서 12장에 맞고, 어떤 결론이든 효과가 있다.
- S6 검토를 S7과 한 호출로 합치는 방식은 설계서 10장(독립 검토를 같은 호출의 자기 점검으로 대체 금지)에 어긋나므로 권하지 않는다.

## 미확인·남은 문제

- 각 시나리오는 1회씩만 실행했다. 시간·토큰의 편차는 측정하지 않았다.
- 후속 update에서 사용자가 알린 "로컬 모델 지원"이 왜 미확인으로 남았는지 확인하지 못했다(위 결론 차이 참고).
- 결론의 품질이 high와 low 사이에 동등한지는 평가하지 않았다. 세 사례의 결론 상태가 같았다는 것만 확인했다.
- 실행 중인 지니 gateway는 아직 이 브랜치 코드가 아니다(재시작하지 않음).
