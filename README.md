# nanobot-easy

UNDER CONSTRUCTION!!! 

**믿고 맡길 수 있는 개인용 AI 에이전트.**

에이전트에게 일을 맡길 때 늘 걸리는 세 가지가 있습니다. *제대로 알아들었을까, 엉뚱한 짓을 하진 않을까, 지난번에 말한 걸 기억할까.* nanobot-easy은 이 세 가지를 **감이 아니라 확인 가능한 형태로** 해결하려는 프로젝트입니다.

[nanobot](https://github.com/HKUDS/nanobot)(홍콩대 HKUDS)에서 분기해 독립적으로 발전시키고 있습니다. 원본이 "가볍고 다재다능한 에이전트"를 지향한다면, 이쪽은 **좁고 깊게 — 정확하고, 안전하고, 초보자도 쓸 수 있게**를 지향합니다.

## 바로 설치하고 실행하기

파일 하나만 받아서 실행하면 나머지는 알아서 됩니다: 필요한 프로그램을 찾아 설치하고, 저장소를 받고, `.venv`를 만들고, WebUI를 빌드하고, 게이트웨이를 띄우고, 브라우저를 엽니다. 브라우저에 뜨는 첫 화면에서 바로 LLM을 연결할 수 있습니다. OpenAI 계정 로그인, X Premium / Grok 구독 계정 로그인, API 키, 내 컴퓨터의 로컬 모델(Ollama, LM Studio 등) 중 편한 방법을 고르면 됩니다.

### macOS

`bootstrap.command` 파일을 받아서 Finder에서 더블클릭하세요. (저장소를 이미 받았다면 저장소 안의 `bootstrap.command`를 더블클릭해도 됩니다.)

### Windows

`bootstrap.bat` 파일을 받아서 탐색기에서 더블클릭하세요.

### Linux

`bootstrap.sh`를 받아서 더블클릭하세요. 배포판/파일관리자에 따라 더블클릭이 안 통하면 터미널에서 실행하세요.

```bash
./bootstrap.sh
```

세 플랫폼 모두 Python 3.11 이상, Git, Node.js/npm(또는 Bun)이 없으면 최대한 자동으로 설치를 시도하고, 안 되면 정확히 무엇을 설치해야 하는지 알려줍니다. 이미 설치되어 있고 게이트웨이가 떠 있는 상태에서 다시 실행하면 재설치 없이 브라우저만 다시 엽니다.

> 원본 `nanobot-ai`와 같은 환경에 동시 설치하지 마세요. 이 저장소는 repo-local `.venv`를 사용해 분리 실행하는 것을 기본으로 합니다.

### 터미널에서 한 줄로

더블클릭 파일을 받기 번거로운 분들을 위한 대안입니다. 동작은 위와 동일합니다.

```bash
curl -fsSL https://raw.githubusercontent.com/ushk-png/nanobot_easy/main/bootstrap.sh | bash    # Linux/macOS
```

```powershell
irm https://raw.githubusercontent.com/ushk-png/nanobot_easy/main/bootstrap.ps1 | iex           # Windows
```

### 직접 하나씩 실행하고 싶다면

저장소를 직접 클론하고 설치·실행 스크립트를 따로 부르고 싶은 분들을 위한 방법입니다.

**Linux / macOS**

```bash
git clone https://github.com/ushk-png/nanobot_easy.git "$HOME/nanobot-easy" && cd "$HOME/nanobot-easy" && ./scripts/install-nanobot-easy.sh
./start-nanobot-easy.sh
```

Ubuntu에서 Python venv 패키지가 아예 없거나 `sudo`를 사용할 수 없는 환경이면 먼저 아래를 실행한 뒤 다시 설치하세요.

```bash
sudo apt update
sudo apt install -y python3 python3-venv python3-pip git curl
```

macOS에 Python 3.11 이상이나 Node.js/npm이 없다면 Homebrew 기준으로 `brew install python node`를 실행한 뒤 다시 실행하세요.

**Windows**

```powershell
git clone https://github.com/ushk-png/nanobot_easy.git "$env:USERPROFILE\nanobot-easy"; cd "$env:USERPROFILE\nanobot-easy"; .\scripts\install.bat
.\start-nanobot.bat
```

Windows 설치 파일은 `.venv`가 없으면 생성하고, WebUI 번들이 없거나 오래됐으면 Node.js/npm 또는 Bun으로 (재)빌드하며, `.local\config.json`이 없으면 기본 설정만 만들고 첫 설정은 브라우저(WebUI)에서 진행합니다. Python이 없으면 python.org에서 Python 3.11 이상을 설치하고, 설치 화면에서 **Add python.exe to PATH**를 켠 뒤 다시 실행하세요. Node.js/npm이 없으면 nodejs.org에서 LTS 버전을 설치한 뒤 다시 실행하세요.

## 무엇이 좋아지나

### 시키는 대로 알아듣습니다 — 그리고 그걸 증명할 수 있습니다

에이전트에 작업 방식(스킬)을 하나둘 추가하다 보면 반드시 겪는 일이 있습니다. **새 스킬을 넣었더니 멀쩡하던 게 엉뚱하게 반응하기 시작하는 것.** 스킬이 서로 트리거를 뺏기 때문인데, 보통은 눈치채지도 못한 채 품질이 무너집니다.

nanobot-easy에서는 스킬마다 "이런 요청은 이 스킬이 잡아야 한다"는 판정 기준이 함께 저장됩니다. `nanobot skill test-routing`을 실행하면 저장된 판정 기준으로 **기존 스킬이 여전히 검색 후보로 잡히는지 회귀 확인**할 수 있습니다. 스킬을 추가한다고 이 검사가 자동으로 돌지는 않으므로 추가·수정 뒤 직접 실행합니다. 이 검사는 검색 순위를 보는 것이며, 모델의 최종 스킬 선택이나 작업 성능을 보장하지 않습니다. 어떤 스킬이 얼마나 자주 불리는지, 기록된 결과가 어떤지도 `nanobot skill stats`로 확인할 수 있습니다.

### 스킬을 직접 쓰지 않아도 됩니다

보통 에이전트에 새 작업 방식을 가르치려면 설정 파일을 손으로 씁니다. 잘 쓰기도 어렵고, 잘못 쓰면 앞의 문제가 터집니다.

여기서는 **필요한 걸 말로 설명하면 초안이 만들어집니다.** 초안을 만들 때 모델이 설계·권한·중복·트리거 충돌 관점의 검토 의견과 판정 문항을 함께 작성합니다. 이 검토는 모델의 판단이므로 위험한 초안을 자동으로 차단한다는 보장은 아닙니다. 초안(draft)은 스킬 검색에 노출되지 않으며, 사람이 내용을 보고 승인해야 사용 후보(candidate)가 됩니다.

### 엉뚱한 짓을 하지 않습니다

자동화를 못 맡기는 진짜 이유는 성능이 아니라 불안입니다. 이 프로젝트는 거기에 실제 장치를 걸었습니다.

- 셸 명령은 `rm -rf` 같은 위험 패턴을 거부하는 가드와 workspace 제한을 거칩니다. 이 가드는 최선 노력 방식이며 프로세스 격리가 아닙니다(격리는 sandbox 설정).
- 파일 삭제·메일 발송처럼 되돌릴 수 없는 작업 전에 의도를 확인하라는 규칙은 주로 프롬프트 지침입니다. 모든 경로에서 코드가 강제하는 권한 경계는 아닙니다. 대상이 모호한 변경 요청을 확인 질문으로 멈추는 코드 경로는 기본으로 꺼진 실험 기능(`contextSelection`)에 있습니다.
- 외부에서 가져온 스킬은 draft로 들어와 승인 전까지 검색·적용 후보에 오르지 않습니다. 실행형 외부 도구 스킬의 설치 출처 허용 목록은 그 기능(기본 꺼짐)을 켠 경우에 적용됩니다.
- 에이전트가 다른 에이전트를 부르는 깊이에 상한이 있어, 위임이 무한히 번지지 않습니다.
- 실행을 요청했는데 실제 작업 없이 “하겠습니다”로 끝내면, 한 번 더 수행하게 하고 그래도 약속만 남으면 미완료로 보고합니다. 이 보정은 새 승인이나 다음 단계 진행을 허용하지 않습니다.
- 파일을 만들거나 고쳤다고 보고하기 전에, 도구가 성공했는지가 아니라 요청한 경로·내용·형식과 맞는지 대조하도록 지침이 안내합니다. 이것도 프롬프트 지침이며 코드가 모든 경로에서 강제하지는 않습니다.
- 대상·결과가 달라질 때만 짧게 되묻고, 그 외에는 가정을 한 줄로 밝힌 뒤 진행합니다. 검토·설명·비교를 부탁받았을 때는 아무것도 바꾸지 않고 결과만 알려주도록 안내합니다.

### 맡긴 일이 끝나면 먼저 알려줍니다

오래 걸리는 작업(설치, 빌드, 코드 수정 실행 등)은 에이전트의 한 번의 답변 안에서 끝나지 않고 뒤에서 계속 돌 수 있습니다. 예전에는 작업이 끝나도 아무도 다시 확인하지 않아서 사용자가 물어봐야 알 수 있었습니다. 이제는 백그라운드 작업이 **스스로 끝나면**(정상 종료, 실패, 시간 초과) 시작한 에이전트가 깨어나 결과를 같은 대화에 보고합니다. 에이전트가 직접 중단시킨 작업은 알리지 않습니다.

코드 수정을 로컬 [Codewhale](./docs/configuration.md#codewhale-tool) 코딩 에이전트에 맡기는 도구(`codewhale`)도 있습니다. **기본으로 꺼져 있고 에이전트마다 켭니다.** 실행 시간 제한 없이 분리 실행되고, 로그에서 권한 거부가 보이는 실행은 종료 코드가 0이어도 성공으로 보고하지 않습니다(로그 문자열로 판단하는 방식이라 모든 경우를 잡지는 못합니다). 코드웨일이 쓰는 모델의 사용 한도에 걸리면 실행되지 않으며, 끝에서 끝까지의 실제 성공 사례는 아직 확인하지 못했습니다([구현 설계서 13.7](./docs/design/skill-framework-implementation-v3.3---14b5c557-d23d-4fec-80ed-09b60e10a786.md)).

### 대화가 쌓일수록 똑똑해집니다

지난주에 말한 프로젝트 이름, 팀원 호칭, 내가 쓰는 약어를 매번 다시 설명하지 않아도 됩니다. 대화를 사건 단위로 저장하고 필요할 때 꺼내 씁니다. 기록은 내 컴퓨터에 남고, 저장된 사건을 검색에서 제외하거나 내용을 지우는 명령이 있습니다. 다만 저장 단계에서 민감 정보를 자동으로 걸러낸다고 보장하지는 않습니다.

대화가 길어져도 기억이 조용히 사라지지 않도록 정리 규칙을 두었습니다. 요약하지 못한 대화를 "정리 끝"으로 표시하지 않고, 아직 Dream이 처리하지 않은 기록은 압축할 때 버리지 않으며, 끝나지 않은 긴 작업의 요청문은 요약으로 잘려 나가지 않게 합니다.

매 대화마다 보내는 입력도 기본으로 가볍게 유지합니다. 도구 설명서는 필요할 때 불러오고, `MEMORY.md`는 예산(기본 5,000토큰) 안의 검토된 요약본을 씁니다. 요약본이 없거나 손상되었거나 예산을 넘으면 원문을 그대로 쓰며 대화를 막지 않습니다. 이 기본값을 끄려면 `agents.defaults.compactContext`를 `false`로, `memoryPromptTokens`를 `0`으로 설정합니다([설정 안내](./docs/configuration.md#compact-context-and-selective-memory)). 입력 토큰이 줄어드는 정도는 작업에 따라 다르며 청구액 절감을 약속하지 않습니다.

### 판단이 필요한 질문은 단계별로 따져 답합니다 (에이전트별로 켜는 기능)

"이 방법이 적합한가", "조건에 맞는 것을 골라 달라", "서로 다른 기록으로 상태를 확정해 달라" 같은 질문은 한 번에 답하면 필수 조건을 빠뜨리거나, 확인되지 않은 정보를 사실처럼 쓰기 쉽습니다. **단계별 추론(지니 방식)**을 켠 에이전트는 이런 질문을 정해진 순서로 처리합니다.

1. 목적·사실·조건을 정리합니다.
2. 각 조건을 판단해 결론과 답변을 냅니다.
3. 그 사이와 끝에서 코드가 확인합니다.
   - 조건 비교·필터·선정은 코드가 직접 계산합니다.
   - 결론이 필수 조건 규칙(필수 조건 미충족이면 부적합)과 맞는지 코드가 검사합니다.
   - 미확인 정보는 충족으로 치지 않습니다.

모델 호출 수는 배치(`--layout`)에 따라 다르며 `two_call` 배치는 보통 2회입니다. 단계별 추론 한 번 실행에는 기본 시간·호출 상한(120초, 8회)이 있습니다. 이 수치는 단계별 추론 경로에만 해당하며, 일반 대화의 호출 수를 보장하지 않습니다. 잡담이나 도구가 필요한 요청은 평소처럼 답합니다.

이 기능은 **기본으로 꺼져 있고, 에이전트마다 명시적으로 적용**합니다. 적용하면 설정에 적용 날짜가 남고, 에이전트를 시작할 때 로그에도 표시됩니다.

```bash
nanobot stepwise apply --config .local/config.<에이전트>.json   # 적용 (백업을 남김)
nanobot stepwise remove --config .local/config.<에이전트>.json  # 해제
nanobot stepwise status --dir .local                          # 어떤 에이전트에 언제 적용됐는지
```

적용하거나 해제한 뒤에는 그 에이전트를 재시작해야 반영됩니다. 동작 방식과 실험 결과는 [단계별 추론 설계서](./docs/design/stepwise-llm-reasoning.md)에 있습니다.

### 개발자가 아니어도 켜서 씁니다

파일 하나(macOS `bootstrap.command`, Windows `bootstrap.bat`, Linux `bootstrap.sh`)를 받아서 실행하면 설치부터 브라우저 온보딩까지 한 번에 끝납니다. 첫 화면에서 모델을 연결하고, 메신저와 도구를 고르면 바로 대화를 시작할 수 있습니다. 홈 화면의 예시 문장을 누르면 입력창에 채워지기만 하니, 내용을 고친 뒤 보내면 됩니다.

여러 에이전트를 한 컴퓨터에서 돌려도 재시작이 안전하도록 했습니다. `nanobot restart`는 돌고 있던 포트로 다시 올라오고, 새로 뜰 수 없는 조건(포트를 다른 프로세스가 잡고 있거나, 설정이 요구하는 환경변수가 현재 셸에 없음)이면 **멈추기 전에** 중단하고 이유를 알려줍니다. 에이전트가 스스로를 재시작하면 그때 하던 작업은 끊기고 자동으로 이어지지 않으니, 작업 중에는 재시작하지 말고 끝난 뒤에 하세요([명령 안내](./docs/cli-reference.md#launcher-commands-up-down-restart)).

> 학생 모드(담임·복습 선생님, 위험 도구 잠금)는 현재 지원하지 않습니다. 브라우저 화면에서 도구 제한이 실제로 적용되지 않는 문제가 있어 선택 화면을 숨겼고, 제한 기능이 갖춰지면 다시 엽니다.

## 이런 일을 맡길 수 있습니다

- 반복 업무 표준화 — 회의록, 보고서, 리뷰 형식을 스킬로 고정
- 의사결정 보조 — 선택지 비교, 장단점 정리, 진단형 질문 응답
- 개발 보조 — 코드 리뷰, 디버깅 절차 안내, 에러 메시지 해설. 완료 보고는 실제로 수행한 검증과 계획만 제시한 단계를 구분합니다([개발 지침](./docs/development.md)). 오래 걸리는 구현은 `codewhale` 도구(기본 꺼짐)로 맡기고 끝나면 알림을 받을 수 있습니다.
- 조사 업무 — 출처가 붙은 리서치 브리프. 짧은 최신 동향·개요는 스킬을 찾거나 읽지 않고 웹 도구로 바로 조사합니다. 조건 여러 개를 연결해야 하거나 핵심 출처가 충돌하거나 조사가 막힌 경우에 심화 조사 스킬을 씁니다. 사용자가 스킬을 지정하면 그대로 따릅니다([복합 조사 안내](./docs/complex-research.md)).
- 학습 보조 — 개념 설명, 복습 질문 만들기

## 원본과의 관계

원본 nanobot에서 2026년 7월 분기한 뒤 독립적으로 운영합니다. 기능을 그대로 따라가지 않습니다. 넓은 채널 연동이나 최신 기능이 필요하다면 [원본](https://github.com/HKUDS/nanobot)이 더 나은 선택입니다.

처음 쓰신다면 [한국어 스킬 사용 가이드](./docs/nanobot-easy-usage-ko.md)부터 보시길 권합니다. 브라우저 화면은 [WebUI 안내](./docs/webui.md), 설정은 [configuration.md](./docs/configuration.md), 모델 연결은 [providers.md](./docs/providers.md)를 참고하세요. Grok 구독 계정으로 연결하려면 [xAI Grok 로그인 안내](./docs/xai-grok-oauth.md)를 보세요. 단계별 추론(지니 방식)은 [단계별 추론 설계서](./docs/design/stepwise-llm-reasoning.md)를 보세요. 구현 상태와 설계/구현 차이는 [구현 설계서 v3.4.16](./docs/design/skill-framework-implementation-v3.3---14b5c557-d23d-4fec-80ed-09b60e10a786.md)(알려진 실패와 남은 결정은 13.7)와 [architecture.md](./docs/architecture.md), 고정 런타임 배포 방법은 [deploy/README.md](./deploy/README.md)에 있습니다. 개별 설계 기록(컨텍스트 경량화, 메모리 정리, 게이트웨이 식별 등)은 [docs/README.md](./docs/README.md#design-records)에서 찾을 수 있습니다.
