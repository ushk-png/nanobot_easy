# 시나리오 체크리스트 — 런타임 수용 검증
(설계서 v3.4.6, 9장 수용 시나리오 기준 / 4단계 수동 검증용)

사용법: 각 시나리오를 실제 나노봇 대화창에 입력하고, "확인 항목"을 직접 조회한 뒤 "합격 조건"과 대조해 Pass/Fail을 기록한다. Fail 시 원인(프롬프트 규칙 누락 / 배선 누락 / 코드 버그) 메모.

공통 확인 위치:
- trace: `.local/workspace/.skillstore/skillstore.db`의 `traces` 테이블
- 최종 스킬 선택: `skill_decision:*` trace의 `selected_skill`, `selection_reason`
- 주제 상태: `workspace/memory/topics/*.md`
- 복합 작업: `workspace/tasks.md` (또는 세션별 경로)
- 세션 원본: `workspace/sessions/<세션키>.jsonl`

## 단일 스킬 시나리오 (S1~S7)

### S1 — 일반 대화, 스킬 불필요
- 입력 예: "안녕", "오늘 날씨 얘기 말고 그냥 파이썬 for문 문법 설명해줘"
- 확인 항목: trace에 해당 턴의 skill_search 호출 기록이 없는가(검색 0회) / 답변이 스킬 형식 지문 없이 자연스러운 일반 답변인가
- 합격 조건: 불필요한 검색·위임 없이 메인이 즉답. 소요 시간 체감상 지연 없음

### S2 — Hot Path 단일 스킬 질문
- 입력 예: "PostgreSQL이랑 MySQL 중에 뭘 써야 해?" (answer-comparison Hot Path 가정)
- 확인 항목: `skill_decision` trace의 `selection_reason` = `hot`, `selected_skill` = `answer-comparison` / 답변에 기준표 + 조건부 결론(무조건 승자 선언 아님) 형식이 있는가
- 합격 조건: 검색 호출 없이(사전 로드) 스킬 Method 형식대로 답변

### S3 — Cold Path 전문 질문
- 입력 예: 카탈로그에 있는 전문 분야 질문(예: "이 회의 내용 회의록 형식으로 정리해줘")
- 확인 항목: `skill_search` trace에 후보·score 기록 존재 / `skill_decision` trace의 `selection_reason` = `cold` 또는 후보 카드 부적합 시 `none` / 실행 위치가 3.4 위임표와 일치(저위험 답변형이면 executed_by=main)
- 합격 조건: 검색 1회로 스킬 발견 → 직접 또는 위임 중 표에 맞는 위치에서 실행

### S4 — 스킬 없는 질문 (후보 카드 부적합)
- 입력 예: 전문적으로 보이지만 현재 카탈로그에 없는 요청. 예: "스타트업 투자계약서에서 liquidation preference 조항이 투자자에게 과도하게 유리한지 검토해줘"처럼 legal 전용 스킬이 없는 영역.
- 확인 항목: `skill_search`가 호출됐는가 / 후보가 있더라도 candidate card(`description`, `when_to_use`, `when_not_to_use`) 기준으로 맞는 스킬이 없다고 판단했는가 / `skill_decision` trace가 `selection_reason=none`인가 / 답변이 스킬 형식을 억지로 씌우지 않고 일반 추론으로 자연스럽게 응답하는가
- 합격 조건: score나 `match_grade`만으로 자동 판정하지 않고, 후보 카드 부적합 시 `skill_decision(none)` 기록 후 일반 추론으로 폴백

### S5 — 후보 경합
- 입력 예: 비교 계열 3종(answer-comparison / compare-options / pros-cons-decision)이 경합할 만한 질문을 5회, 표현을 바꿔 반복
- 확인 항목: 5회의 `skill_decision.selected_skill`이 동일한가 / 1·2위 점수차와 conflicts_with 플래그 여부
- 합격 조건: 관계 배선 후 5/5 동일 스킬 선택(불안정하면 Fail, 2단계 배선 누락 의심)

### S6 — 후속 질문 위임 (컨텍스트 패키징)
- 입력 예: 문서를 언급하며 대화 시작 → 몇 턴 뒤 "아까 그 문서에서 리스크 부분만 다시 정리해줘"
- 확인 항목: delegate/spawn 호출의 task 문자열에 대명사("아까 그") 대신 파일 경로·요지가 실제로 담겼는가(trace 또는 로그로 task 원문 확인) / 게이트 결과가 ok인가
- 합격 조건: 서브에이전트가 맥락 없이도 자기완결적 task로 성공. Fail 시 3.3 규칙이 프롬프트에 반영됐는지 확인

### S7 — exec 필요 스킬
- 입력 예: "yq로 이 yaml 파일 특정 필드만 뽑아줘" (requires_exec=true 스킬)
- 확인 항목: trace의 `executed_by`가 `main`이 아니라 exec 권한 프로파일명인가 / 해당 프로파일 레지스트리에 exec 존재, 반대로 researcher 등에는 부재(하네스 회귀와 교차 확인)
- 합격 조건: 메인이 직접 실행하지 않고 올바른 프로파일로 위임, 실행 성공

## 복합 작업 시나리오 (C1~C5)

### C1 — 순차 의존 복합
- 입력 예: "이 문서 요약하고 사업성도 검토해줘"
- 확인 항목: tasks.md에 하위 작업 2개 기록 / `skill_search`가 wave 1과 wave 2로 분리 호출됐는가(1회 batch에 두 작업을 같이 넣으면 Fail) / trace에 `wave_no` 1, 2 존재 / 웨이브2의 context에 웨이브1 출력이 패키징됐는가 / 최종 답변에 스킬별 출처 표기
- 합격 조건: 2웨이브로 순차 실행, 사업성 검토가 요약 결과를 실제로 참조, `skill_search`와 `skill_decision` trace에 wave_no 1·2가 남음

### C2 — 독립 병렬 복합
- 입력 예: "문서 3개 각각 요약해줘" (서로 무관한 문서)
- 확인 항목: tasks.md의 3개 하위 작업이 동일 `wave_no`(1웨이브) / skill_search가 배치 1회 호출(개별 3회 아님) / 병렬 spawn 확인
- 합격 조건: 1웨이브 병렬 실행, 검색 왕복 1회

### C3 — 부분 실패
- 입력 예: "요약하고, 이 스크립트 실행하고, 결과 검토해줘" 중 스크립트 실행 단계를 의도적으로 실패시킴(없는 파일 지정 등)
- 확인 항목: 실패 단계 게이트 result=error, 의존 후행 작업이 Skipped로 표기 / 독립 작업은 계속 진행됐는가 / 최종 답변에 부분 결과+실패 원인+Skipped 목록이 명시됐는가
- 합격 조건: 전체가 멈추지 않고 부분 결과·원인이 투명하게 보고됨

### C4 — 오발동 자기 수정
- 입력 예: 복합처럼 보이지만 실제론 단일 스킬로 충분한 질문("이 코드 리뷰해줘" 정도의 단순 요청)
- 확인 항목: composite-task가 발동했더라도 분해 결과가 1개면 즉시 종료하고 단일 스킬 흐름 전환했는가(trace에 composite 관련 흔적이 남되 실제 처리는 단일 스킬 경로)
- 합격 조건: 불필요하게 tasks.md·웨이브 구조가 남지 않고 매끄럽게 단일 처리

### C5 — 웨이브 간 재계획
- 입력 예: "이 코드 분석하고 문제 있으면 고쳐줘"
- 확인 항목: 웨이브1(분석) 완료 후 웨이브2(수정)의 하위 작업 정의가 웨이브1 출력에 따라 구체화됐는가(분석 결과에 없던 구체적 수정 대상이 웨이브2 task에 반영) / 신규 작업 추가가 있었다면 1회로 제한됐는가
- 합격 조건: 정적 계획이 아니라 실제로 재계획이 일어남

## 메모리·주제 시나리오 (T1~T2)

### T1 — 멀티토픽 복귀
- 절차: 코딩 주제로 대화 → 스케줄 등록 요청 → 잡담 → "아까 코딩 이어서"
- 확인 항목: 주제 전환 시점에 `memory/topics/<코딩>.md`가 생성·갱신됐는가(결정 사항/미해결/다음 단계/파일 경로 포함) / 복귀 요청 시 topic-recall이 이 파일을 먼저 참조했는가(요약 손실 없이 세부 식별자가 복원되는지 — 예: 변수명·파일명이 정확히 되살아나는지)
- 합격 조건: 복귀 답변이 대화 앞부분 재요약이 아니라 topics/ 파일 기반의 정확한 상태 복원

### T2 — topics 파일 부재 시 세션 재구성
- 절차: topics/ 파일이 아직 없는(스냅샷 규칙 반영 전) 과거 세션에서 "그때 그 얘기 이어서" 요청
- 확인 항목: topic-recall이 `memory/topics/` 확인 → 없거나 부족하면 `memory/history.jsonl` 확인 → 그래도 부족하면 `sessions/<세션키>.jsonl` 원문 확인 순서를 지켰는가 / history만으로 파일명·함수명·값 등 세부 식별자가 충분히 복원되면 sessions 원문 생략 가능 / 원문 세션이 크고 history가 부족하면 재구성이 서브에이전트로 위임됐는가(3.4 대량 컨텍스트 조건)
- 합격 조건: topics/ 없이도 폴백 사슬에 따라 주제 특정 및 복원 성공, 복원에 필요한 세부 식별자 정확, 지어냄 없음. 후보 주제가 2개 이상이거나 식별 근거가 없으면 추측하지 않고 후보를 제시하며 사용자에게 확인. 후보가 명백히 1개면 답변 서두에 복원 대상을 명시.

## Composer 시나리오 (P1)

### P1 — 스킬 생성 요청 → 등록
- 입력 예: "방금 한 작업 스킬로 만들어줘" 또는 웹 UI 위저드
- 확인 항목: 사용자 요청 없이 자발적 compose가 없었는지(제안까지만 있었는지) / drafts/compose 호출 → 202+draft_id / 검토 리포트(보안/활용성/중복/트리거차별화) 4종 생성 / 라우팅 테스트 10문항 생성 및 결과 표시 / 적신호 없으면 원클릭 등록, 있으면 접힘 해제되어 확인 강제 / 승인 후 candidate로 검색 노출(승인 전에는 미노출 확인)
- 합격 조건: 전 구간 E2E 성공. 추가로 system 스킬(composite-task 등) 수정 시도 시 403/거부 확인, capability 플래그 off 시 관리 API 전체 차단 확인
