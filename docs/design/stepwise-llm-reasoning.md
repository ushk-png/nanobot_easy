# 코드 주축 단계별 LLM 추론 시스템 통합 설계서 v3.1

동적 절차 생성·즉시 실행·실행 중 변경 통합

작성일: 2026년 10월 9일  
문서 성격: 구현용 아키텍처와 동작 계약. 특정 언어·프레임워크의 세부 코드는 구현자가 선택한다.

## 1. 설계 목적과 핵심 원칙

이 시스템의 목적은 코드로 논리적인 사고 절차를 정의하고, LLM이 각 단계에 필요한 해석과 판단을 수행하도록 하여 답변의 논리적 연결과 일관성을 높이는 것이다.

코드는 사고 절차의 선택, 단계 순서, 입력·출력 계약, 검증, 분기, 복귀, 종료를 통제한다. LLM은 사용자 상황과 원문의 의미를 해석하고 단계별 판단 결과를 제출한다. Z3와 일반 코드는 계산하거나 형식화할 수 있는 부분을 처리한다.

등록된 절차가 없거나 현재 요청에 맞지 않으면 LLM이 절차를 즉석 생성하거나 기존 절차를 수정할 수 있다. 코드가 구조와 실행 조건을 검사하고 목적 적합성 검토가 통과하면, 재사용 등록이나 사람의 별도 승인 없이 해당 요청에서 즉시 실행한다. 실행 권한은 사용자가 요청한 작업과 시스템이 제공하는 도구 범위 안에 있으며, 절차 생성만으로 새로운 외부 작업 권한이 생기지는 않는다.

코드로 통제하는 것은 실행 규칙과 단계 계약이다. 개별 업무의 모든 단계와 순서를 미리 작성해야 하는 것은 아니다. 한 번의 요청에서 실행할 수 있는 상태와 여러 요청에 재사용할 만큼 평가된 상태를 구분한다.

기본 운영 목표는 모델의 별도 thinking 모드를 사용하지 않고 외부 절차로 단계적 추론을 수행하는 것이다. 다양한 완성 답변을 반복 생성해 다수결로 선택하거나, 모든 요청을 후보 탐색 트리로 푸는 방식은 기본 구조에 포함하지 않는다. 대안 비교가 필요한 업무의 특정 단계에서만 후보 생성을 사용한다.

별도 thinking 모드를 끄더라도 LLM의 언어 이해와 의미 판단 능력은 계속 사용한다. 그 설정을 지원하는 모델·실행 환경인지 먼저 확인해야 한다. 추론 내용의 표시만 숨긴 상태는 비활성화로 간주하지 않는다. 비활성화가 불가능하면 호환 모델을 사용하거나 해당 운영 모드가 지원되지 않음을 표시한다. 기존 추론 모드로 조용히 복귀하지 않는다.

전체 목표는 세 가지로 구분한다.

1. 절차 통제: 필요한 판단을 순서대로 수행하고 근거와 결론을 연결한다.
2. 기능 대체: 내부 thinking을 끈 상태에서 해당 업무의 요구 품질을 달성한다.
3. 효율: 업무 완료까지의 총토큰과 지연을 관리한다.

기능 대체와 토큰 절감은 각각 평가한다. 절차 준수만으로 모든 의미 판단이 옳아지거나 기존 추론 모델보다 좋아진다고 보장하지 않는다.

|코드 오케스트레이터|단계별 사고 절차와 계약을 실제로 실행하는 중심 엔진|
|LLM 개별 판단|명확한 질문과 입력 범위를 가진 단계별 판단 함수|
|근거·미확인 정보 관리|모든 단계가 공유하는 상태 저장소와 의존 관계|

|최종 답변 검사|확정된 판단·조건·검증 범위를 전달하는 마지막 단계|

|동적 절차 생성|미등록·부적합 요청에 절차를 생성·검사하고 같은 실행 엔진에서 즉시 수행|

기존 v2.1의 ‘규칙 추출 1회와 템플릿 답변’은 간단한 규칙 업무에 맞는 축약 절차로 남긴다. 일반 평가·문제 해결은 단계별 판단을 거치는 표준 또는 동적 절차로 확장한다. 이전의 호출 수·토큰 절감 예시는 축약 경로에 관한 가정이므로 본 설계 전체의 성능 예측으로 사용하지 않는다.

## 3. 구성 요소와 책임

|구성 요소|책임|제한|
|---|---|---|
|절차 레지스트리|표준·동적 절차의 정의, 적용 조건, 상태, 버전 저장|현재 요청의 실행 허용과 검증된 재사용 등록을 구분|
|절차 선택기|목적에 맞는 절차의 재사용·수정·신규 생성 경로 선택|단순 키워드만으로 모호한 요청을 확정하지 않음|
|절차 생성기|기존 절차 수정 또는 새 단계·질문·연결을 구조화해 제안|실행 허용 상태와 필수 검사 정책을 스스로 변경하지 않음|
|절차 검사기|구조·데이터 연결·목적 대응·실행 조건 검사|형식 검사 통과를 절차의 의미적 완전성 증명으로 취급하지 않음|
|실행 제어기|현재 단계, 선행 조건, 분기, 예산, 복귀·재개 관리|LLM의 임의 지시로 필수 단계를 우회하지 않음|
|단계별 LLM 호출기|필요한 입력을 전달하고 구조화된 판단 수신|절차 변경은 제안으로 제출하며 검사 없이 흐름을 변경하지 않음|
|상태·근거 저장소|사실, 가정, 판단, 근거, 의존 관계와 이력 유지|과거 버전의 결과를 현재 결과로 혼용하지 않음|
|검사기|구조·의미·계산·논리 등 정의된 검사 실행|검사 범위 밖의 정확성을 보장하지 않음|
|답변 작성기|최종 판단과 조건을 사용자 표현으로 전달|새 사실·기준을 추가해 결론을 바꾸지 않음|
|측정기|품질, 호출, 토큰, 지연, 복귀 원인 기록|보류·실패 사례의 비용을 통계에서 제외하지 않음|

이 문서에서 실행 허용은 절차 검사 결과에 따라 코드가 부여하는 상태다. 동적 절차 실행에 매번 사람의 승인을 추가하지 않는다. 재사용 등록도 사전에 정의한 평가 기준을 충족하면 자동으로 수행할 수 있다. 도구별로 원래 필요한 사용자 권한은 그대로 적용한다.

## 4. 사고 절차의 선택과 조합

### 4.1 기본 절차

|업무|논리적 단계|
|---|---|
|방법·제안 평가|목적 → 사실 → 평가 기준 → 기준별 판단 → 종합 결론 → 점검 → 답변|
|원인분석|문제 정의 → 사실·시간순서 → 인과관계 검토 → 원인 판단 → 조치 연결 → 점검 → 답변|
|문제 해결|현재·목표 상태 → 차이와 제약 → 해결 방안 → 실행 조건 → 제안 → 점검 → 답변|
|문서 검토|작성 목적 → 주장·근거 → 누락·모순 → 수정 방향 → 수정안 → 점검|
|규칙 판단|적용 규정·사실 → 누락·예외 확인 → 코드·Z3 판정 → 조건을 포함한 답변|
|단순 조회·대화|요청 해석과 필요한 근거 확보 → 직접 답변|

절차는 판단 순서와 검사 기준을 제공한다. 예를 들어 원인분석 절차를 통과했다는 사실만으로 원인이 입증된 것은 아니다. 인과 판단에는 관측 근거와 대안 설명 검토가 필요하다.

### 4.2 선택 정책

명시적으로 선택된 기능·도메인이 있으면 이를 우선 사용한다. 자연어 요청은 최초 LLM 호출에서 목적·제약·제안 절차를 함께 추출하고 코드가 적합성을 확인한다. 모든 요청 앞에 별도 의도 분류 호출을 추가하지 않는다.

확신도 자체 보고나 반복 해석 빈도를 사용자 의도의 정답 확률로 취급하지 않는다. 의도 후보에 따라 답변 또는 실행 대상이 크게 달라지면 확인 질문을 한다. 사실이 부족한 경우에는 의도 질문과 구분해 필요한 사실을 묻는다. 확인 질문에는 후보 외의 설명을 받을 수 있는 경로를 둔다.

복합 요청은 기존 절차와 필요한 동적 단계를 연결한다. 예를 들어 문서 검토 후 수정안 작성은 검토 결과를 수정 절차의 입력으로 전달한다. 목표와 공통 사실은 공유하되 하위 작업별 상태와 완료 조건은 구분한다. 각각 검토된 절차도 연결 방식이 달라지면 새 연결 관계를 검사한다.

|경로|선택 기준|처리|
|---|---|---|
|재사용|목적·입력·필수 조건·도구 범위에 맞는 절차가 있음|현재 요청과 버전의 적합성을 확인하고 실행|
|수정|기존 절차의 큰 흐름은 맞고 일부 질문·단계·연결 변경이 필요|원본을 보존한 새 버전 제안, 변경부와 영향 경로 검사 후 실행|
|신규 생성|기존 절차를 맞추면 목적 누락이나 불필요한 단계가 커짐|요청에 맞는 구조화 절차 생성, 검사 후 즉시 실행|

새로운 유형이라는 이유만으로 거절하거나 재사용 등록을 기다리지 않는다. 절차 생성에 필요한 핵심 정보가 없으면 질문하고, 사용 가능한 도구로 해결할 수 없는 부분은 미해결로 표시한다. 절차 생성도 비추론 모드를 기본으로 하며 구조화된 계획을 출력한다.

### 4.3 생성되는 절차의 형식

LLM이 제출하는 것은 기존 실행 엔진이 읽는 절차 정의다. 구체적인 직렬화 형식은 JSON 등으로 선택할 수 있다. 새로운 업무별 단계 질문과 기준을 작성할 수 있으며 기존 도메인 이름에 제한하지 않는다. 실행은 해석·추출·평가·조회·계산·검증·질문·출력 등 엔진이 지원하는 연산으로 구성한다.

|필드|내용|
|---|---|
|목적·요구사항|사용자 요청에서 추출한 목표와 필수 제약의 식별자|
|단계|ID, 연산 종류, 단계별 질문, 입력·출력 계약|
|연결|선행 단계, 입력을 제공하는 산출물, 조건별 다음 단계|
|요구사항 대응|어느 단계·검사가 각 사용자 요구를 처리하는지|
|검사|필수 코드 검사와 목적 적합성·근거 의미 검사|
|예외·종료|정보 부족, 도구 실패, 예산 초과, 완료 시의 경로|
|예산·범위|단계 수·호출·시간·복구 상한과 사용할 수 있는 도구|
|버전·생성 근거|부모 절차, 변경 이유, 적용 요청과 입력 버전|

구조화된 분기식은 엔진의 제한된 연산자로 해석한다. 절차 문자열을 임의 Python 코드로 평가하는 방식은 기본 구현에 사용하지 않는다. 계산 코드 생성이 필요한 업무는 이미 제공되는 코드 실행 도구의 계약으로 처리한다. 새 연산·도구 자체의 구현은 절차 생성과 구분한다.

### 4.4 실행 전 검사

검사는 두 층으로 나눈다. 코드가 구조와 실행 조건을 확인하고, LLM 검토가 원래 요청과 절차의 의미적 적합성을 평가한다.

|검사|주요 확인 사항|
|---|---|
|구조·형식|단계 ID의 유일성, 계약 필드, 사용 가능한 연산·검사기|
|데이터 연결|참조한 산출물의 존재, 입력·출력 자료형, 분기별 필요한 값의 가용성|
|순서·분기|필수 선행 단계, 도달할 수 없는 단계, 누락된 분기와 기본 처리|
|종료·예산|모든 경로의 완료·질문·중단 경로, 제한된 복귀, 총 실행 예산|
|목적 대응|사용자 요구와 제약이 어떤 단계에서 처리되는지, 불필요하거나 빠진 판단|
|필수 정책|출처·미확인 상태 유지, 필수 검사 보존, 허용된 도구 범위|

일반 의존 관계는 순환이 없는 구조로 만들고, 재시도·복귀는 횟수 제한이 있는 별도 전이로 표현한다. 합류 단계는 해당 경로에서 실제 생성된 값만 사용하게 한다. 자료형이 같더라도 의미나 단위가 맞는지는 별도 검사 대상이다.

필수 검사 목록은 엔진 정책과 업무 요구사항에서 결정하고 생성 절차에 추가할 수 있다. LLM이 검사 목록을 비우거나 예산을 임의 확대해 통과할 수 없게 한다. 요청별 의미 대응표를 만들었다는 사실만으로 누락이 없다고 단정하지 않는다.

새로 생성하거나 의미가 바뀐 절차에는 실행 전 목적 적합성 검토를 수행한다. 검토 입력은 원래 요청·제약과 절차 정의이며, 생성기의 ‘적절함’ 자기평가를 통과 근거로 삼지 않는다. 별도 LLM 호출로 검토해도 같은 오류를 반복할 수 있으므로 실행 중 단계 검사와 결과 검사를 계속 적용한다. 의미 검토는 수학적 증명이 아니다.

### 4.5 검사 후 즉시 실행과 실패 처리

절차 생성 → 코드 구조 검사 → 목적 적합성 검토 → 해당 버전에 실행 허용 부여 → 기존 실행 엔진으로 수행한다. 실행 허용은 절차 버전·요청·입력 계약·도구 범위에 묶는다. 절차가 변경되면 이전 허용 상태를 그대로 상속하지 않는다.

결함이 있으면 생성기에 결함과 관련 부분만 전달해 제한된 횟수로 수정한다. 핵심 정보가 부족하면 사용자에게 질문한다. 예산 내에 유효한 절차를 만들지 못하면, 현재 요구를 충족하는 기존 절차로 돌아가거나 부분 결과·미해결을 반환한다. 불완전한 절차를 강제로 실행하지 않는다.

### 4.6 실행 허용과 재사용 등록의 생명주기

|상태|의미|
|---|---|
|초안|생성됐으나 필수 검사가 완료되지 않음|
|요청별 실행 허용|필수 검사를 통과해 현재 요청에서 즉시 실행 가능|
|실행 완료·중단|실행 결과와 오류·비용 기록이 남음|
|재사용 후보|후속 평가를 위해 보관한 절차, 새로운 요청의 기본 절차는 아님|
|재사용 등록|별도 사례 평가 기준을 충족하고 적용 범위를 정한 절차|
|사용 중지|반복 결함·호환성 문제 등으로 새 실행에 사용하지 않음|

한 번 완료됐다는 이유로 재사용 등록하지 않는다. 사용자 요구 충족, 독립된 평가 사례, 누락·충돌 처리, 비용과 적용 범위를 확인한다. 재사용 후보를 다른 요청에 시험할 수 있지만 해당 요청의 적합성·실행 전 검사를 다시 수행한다. 특정 사용자의 원문·개인 사실을 일반 절차 정의에 복사하지 않고 실행 기록과 절차 템플릿을 분리한다.

### 4.7 실행 중 절차 변경

새 정보로 현재 절차가 부적합해지면 LLM이 변경 이유·변경 단계·영향받는 산출물을 제출한다. 실행 중인 정의를 덮어쓰지 않고 새 버전을 만든다. 코드가 변경 범위와 전체 의존·분기 관계를 검사하고, 의미가 달라진 부분은 목적 적합성 검토를 다시 수행한다.

전환 시 현재 상태를 체크포인트로 남기고 이전 버전에 속한 미완료 실행은 취소하거나 결과 반영을 차단한다. 변경 단계와 그 후속 의존 결과를 무효화한다. 입력·계약·사실 버전이 그대로인 결과만 재사용한다. 새 버전으로 원자적으로 전환하고 유효한 선행 결과가 확보된 지점부터 재개한다.

절차 수정으로 이미 수행한 외부 작업이 취소되거나 되돌려진 것으로 간주하지 않는다. 외부 작업 결과는 별도 기록을 유지하고 중복 실행을 막는다. 변경이 검사를 통과하지 못하면 이전 절차가 여전히 목적에 맞는 경우에만 이어서 실행하며, 그렇지 않으면 질문·부분 결과·중단으로 처리한다.

## 5. 표준 사고 절차: 방법 평가

다음은 ‘이 방법이 사용자 목적에 적합한가?’를 처리하는 기준 절차다. 다른 업무도 같은 단계 계약을 사용하되 판단 질문과 산출물을 바꾼다.

|단계|입력|LLM 또는 코드의 과제|산출물|통과 조건·실패 처리|
|---|---|---|---|---|
|S1 목적 파악|현재 요청, 관련 사용자 제약|달성 목표·평가 대상·필수 제약 구분|목표와 제약 목록|핵심 모호성이 남으면 질문, 작은 가정은 표시|
|S2 사실 정리|원문·조회 자료·S1|사실·추정·미확인·충돌 구분|출처가 연결된 사실 목록|필수 사실 부족 시 조회·질문 또는 조건부 진행|
|S3 평가 기준|S1·S2·등록된 기준|목적을 판정 가능한 기준으로 구체화|필수·선호 기준과 판정 방법|목적 대응과 예외 범위 확인, 부적합하면 S3 수정|
|S4 기준별 판단|확정된 기준·관련 사실|각 기준의 충족 여부와 근거 판단|충족·불충족·미확인 및 근거|필수 기준 누락 차단, 사실 오류면 S2, 기준 오류면 S3|
|S5 종합 결론|S4·종합 규칙|필수 조건·예외·선호를 반영해 결론 도출|결론과 적용 조건|미확인을 참으로 승격하지 않음, 판단 충돌 시 해당 단계 복귀|
|S6 논리·근거 점검|주요 결론과 의존 근거|구조·의미·형식 논리를 필요한 범위에서 검사|검사별 상태와 결함 목록|요구된 검사가 끝나야 진행, 결함별 복귀 지점 결정|
|S7 답변 작성|통과한 결론·근거·제한 사항|사용자에게 필요한 답변 작성|최종 답변|조건·수치·대상 유지 검사, 새 주장 발견 시 삭제 또는 앞 단계 재검토|

S3에서 필수 기준과 선호 기준을 구분한다. 필수 조건 위반을 선호 점수로 상쇄하지 않는다. 단, 실제 업무 규칙이 상쇄나 예외를 허용하면 그 규칙을 명시한다. 주관적 가중치는 출처 또는 설정 근거를 남기고 객관적 사실처럼 다루지 않는다.

S5의 결론은 ‘적합’, ‘조건부 적합’, ‘부적합’, ‘판단 보류’ 등 업무 상태로 표현할 수 있다. 이 상태와 Z3 검사 결과는 별도 필드다. ‘적합’이라는 의미 판단 자체를 Z3 증명으로 표시하지 않는다.

## 6. 단계 계약과 실행 상태

### 6.1 각 단계에 필요한 정의

|계약 항목|필수 의미|
|---|---|
|목적·질문|이번 단계에서 판단할 한정된 대상|
|입력 명세|허용하는 정보와 필요한 선행 결과|
|출력 명세|판단 결과, 근거 위치, 가정, 미확인 사항|
|검사 목록|구조 검사, 의미 검사, 도구 검사와 필수 여부|
|진행 조건|완료·조건부 진행·정보 요청·복귀·중단의 조건|
|수정 범위|이 단계가 작성·변경할 수 있는 객체|
|실패 경로|오류 종류와 돌아갈 단계|
|예산|입력·출력·호출·시간·복구 상한|
|버전|절차·프롬프트·규칙·스키마의 버전|

‘근거가 존재한다’는 코드 검사와 ‘그 근거가 주장을 뒷받침한다’는 의미 검사를 구분한다. 후자는 LLM 검토·도구 확인·사람 평가가 필요할 수 있다. 같은 모델의 의미 검토도 틀릴 수 있으며 독립적인 증명으로 표시하지 않는다.

### 6.2 실행 상태

단계 실행 상태는 대기, 실행 중, 통과, 조건부 통과, 정보 대기, 수정 필요, 무효화, 중단으로 구분한다. 이는 사실의 참·거짓 또는 논리 검증 상태와 다른 축이다.

‘통과’는 해당 단계에 정의한 계약과 검사 요건이 충족됐다는 뜻이다. 현실적 진실을 보장한다는 뜻이 아니다. 검사하지 않은 항목을 통과한 것으로 채우지 않는다. 의미 검사가 필수인 단계는 그 검사가 생략되면 정상 통과하지 못한다.

조건부 통과는 해당 절차가 미확인 정보를 가정으로 넘기는 것을 허용할 때만 가능하다. 다음 단계에 가정과 의존 관계가 전달돼야 하며, 최종 결론에 조건을 남긴다. 중요한 사실이 없어 유효한 결론을 만들 수 없으면 정보 대기 또는 판단 보류로 종료한다.

### 6.3 상태 전이의 소유권

LLM은 판단·질문·수정 필요성을 제안한다. 코드가 계약에 따라 상태 전이를 실행한다. 모델이 출력한 ‘검증됨’ 문자열을 시스템 검증 상태로 사용하지 않는다. 검사 결과는 해당 검사기가 생성한 결과로만 기록한다.

동적 절차에서도 같은 계약을 적용한다. 개별 단계 실행 상태와 절차 전체의 실행 허용·재사용 상태는 별도로 저장한다. 단계가 통과했다고 새 절차 버전 전체가 자동으로 실행 허용되는 것은 아니다.

## 7. 상태 저장과 근거 연결

저장 단위는 장문의 사고 서술보다 재검사 가능한 사실·기준·판단·결론이다. 구현은 일반 DB로 시작할 수 있고 별도 그래프 DB를 필수로 요구하지 않는다.

|객체|핵심 필드|
|---|---|
|업무|요청, 목표, 절차 버전, 재사용·수정·신규 생성 경로, 전체 상태, 예산|
|절차|정의, 부모 버전, 생성·변경 이유, 적용 범위, 요구사항 대응표, 실행 허용·재사용 상태|
|사실|값·명제, 출처·원문 위치, 시점·단위, 확인·추정·미확인 상태|
|기준|목적 연결, 필수·선호 구분, 판정 방법, 출처·적용 범위|
|판단|기준 ID, 결과, 근거 ID, 가정, 작성 단계|
|결론|의존 판단 ID, 적용 조건, 결론 범위|
|검사|절차 또는 산출물의 대상 버전, 검사 종류, 결과, 한계, 반례·충돌 자료|
|이력|변경 대상, 이전·이후 버전, 변경 근거, 무효화된 후속 결과|

사용자 발언은 출처가 명확한 정보지만, 필요한 경우 관측 자료와 구분한다. ‘자료가 없다’와 ‘그 사실이 거짓이다’를 혼동하지 않는다. LLM이 추정한 값은 새 근거 없이 확인된 사실이 될 수 없다.

판단마다 사용한 사실과 기준을 연결한다. 사실 또는 기준이 수정되면 그 항목에 의존하는 판단·결론·검사를 모두 무효화하고 필요한 부분을 다시 수행한다. 관련 없는 결과는 버전과 적용 범위가 여전히 맞으면 재사용한다.

사용자 후속 답변으로 목적이 바뀌면 S1부터 영향 범위를 판단한다. 예전 제약을 무조건 유지하거나 모두 삭제하지 않고, 유효한 제약을 갱신한다. 재개 시 업무 버전과 상태를 확인해 이전 실행 결과를 중복 반영하지 않는다.

## 8. 검증 도구의 분담

|검사 종류|담당|검사 범위|
|---|---|---|
|구조|코드|필수 필드·자료형·참조 ID·전체 기준의 판단 여부|
|단순 업무 규칙|코드|개수·날짜·범위·고정 계산·분기 조건|
|근거 의미|LLM 또는 적합한 검토 절차|주장과 원문의 의미 대응·누락·과도한 일반화|
|형식 논리|Z3|전제 일관성·논리적 귀결·제약 충족|
|실행 결과|프로그램·테스트·조회 도구|계산 결과·실행 동작·외부 자료 확인|

Z3는 형식화할 가치가 있는 부분에만 사용한다. 논리식을 만들었다는 사실만으로 표현의 타당성이 확보되지 않는다. 자연어의 필요조건·충분조건·부정·예외·시간 범위를 보존하고 원문과 연결한다.

반복 사용되는 규정은 검토된 규칙을 등록하고 코드는 그 규칙을 불러와 적용한다. 상황별 평가 기준은 LLM이 제안할 수 있으나 기준 자체가 임시 판단임을 구분하고 S3에서 점검한다. 주관적 기준을 임의로 동치식으로 만들어 객관적 평가처럼 표시하지 않는다.

### 8.1 결론의 논리적 귀결 검사

B는 규칙·사실·명시적 가정, C는 검증할 결론이다. C 자체를 B에 포함해 자기 자신을 증명하지 않는다.

1. B가 sat인지 검사한다. unsat이면 전제 충돌, unknown이면 이 절차의 검증 미완료로 종료한다.
2. B가 sat이고 B ∧ ¬C가 unsat이면 C는 주어진 전제에서 반드시 따라온다.
3. B ∧ ¬C가 sat이면 B ∧ C도 검사한다. 후자가 unsat이면 ¬C가 반드시 따라온다.
4. 두 식이 모두 sat이면 결론과 반대 결론이 모두 가능하다. 현재 전제로는 미확정이다.
5. 필요한 검사에서 unknown이 나오면 해당 판단을 확정하지 않는다.

|검증 상태|의미|
|---|---|
|ENTAILED|주어진 일관된 전제에서 C가 반드시 성립|
|REFUTED|주어진 일관된 전제에서 ¬C가 반드시 성립|
|UNDETERMINED|C와 ¬C가 모두 가능한 상태|
|INCONSISTENT|전제끼리 충돌|
|SOLVER_UNKNOWN|필요한 솔버 검사를 완료하지 못함|

일정 같은 제약 풀이에서는 sat과 구체적인 해를 얻으면 ‘입력한 제약을 만족하는 해를 찾음’으로 표시한다. 현실의 미확인 사실에 솔버가 할당한 값을 실제 관측값으로 취급하지 않는다. 최적화도 가능한 해와 최적성이 확인된 해를 구분한다.

형식적 보장 범위는 다음과 같다. 형식화가 의도한 의미를 정확히 표현하고 전제가 참이며 서로 일관되고 논리적 귀결 검사가 통과했다면, 그 결론은 주어진 전제에서 반드시 따라온다. 사실·의도·표현의 정확성과 조건의 완전성은 별도 관리 대상이다.

## 9. 복귀와 수정 정책

아래 S1~S7은 표준 평가 절차의 예시다. 동적 절차에서는 해당 사실·기준·판단을 만든 단계 ID와 의존 관계를 이용해 복귀 지점을 결정한다. 새로운 순서가 필요하면 4.7의 절차 버전 변경 절차를 적용한다.

|문제|복귀·조치|변경 제한|
|---|---|---|
|사용자 목적 오해|S1|영향받는 기준부터 후속 결과 무효화|
|자료 누락·추출 오류·사실 충돌|S2|원문·조회·사용자 확인에 근거해 수정|
|기준이 목적과 맞지 않음|S3|기준 변경 이유를 기록하고 관련 판단 재실행|
|근거가 판단을 뒷받침하지 않음|S4 또는 S2|근거를 꾸며 내거나 미확인을 참으로 바꾸지 않음|
|개별 판단과 결론 불일치|S5|사실을 바꾸지 않고 종합 규칙·결론 점검|
|조건식 번역 오류|해당 형식화 단계|원문 의미를 보존하는 수정만 허용|
|표현 과정에서 조건 누락|S7|검증된 상태 객체를 기준으로 다시 작성|
|절차 자체가 목적을 충족하지 못함|절차 생성·변경 단계|새 버전 검사 후 영향받는 결과를 무효화하고 재개|
|예산 초과·반복 실패|중단 또는 부분 결과|미완료를 정상 완료로 표시하지 않음|

unsat core는 모순을 이루는 조건들의 일부이며 잘못된 조건의 정답이나 근본원인은 아니다. 기본적으로 최소 크기의 집합도 보장하지 않는다. 원문 확인을 위한 단서로 사용한다.

복구 시 관련 입력과 결함만 전달하되 의미 판단에 필요한 주변 조건을 유지한다. 동일 상태가 반복되거나 새 근거 없이 값만 바뀌면 중단한다. 복귀 횟수와 총 호출·시간 상한은 절차별 설정으로 관리한다.

실제 외부 변경 작업이 연결된 경우, 판단 단계의 재실행이 이미 완료된 변경 작업을 자동 반복하지 않도록 실행 결과와 중복 방지 식별자를 별도로 유지한다.

## 10. 논리적 단계와 실제 LLM 호출의 분리

단계가 일곱 개라고 반드시 일곱 번 호출하는 것은 아니다. 다만 중간에 코드가 통과 여부를 결정해야 하는 단계는 별도 실행 경계를 유지한다.

|병합 가능한 경우|분리해야 하는 경우|
|---|---|
|목적과 기본 사실을 같은 입력에서 추출|앞 단계 승인 결과에 따라 다음 질문이 달라짐|
|서로 독립적인 여러 기준의 판단을 한 번에 요청|조회·계산·Z3 결과를 받아야 다음 판단이 가능|
|확정된 결과의 설명과 문장 다듬기|별도 의미 검토가 필수인 단계|
|필수 중간 검사 없이 진행 가능한 단순 작업|기준이 통과하기 전에 그 기준으로 결론을 만들 위험이 큼|

병합한 호출 안에서 여러 산출물을 만들었더라도 코드가 나중에 검사한 결과를 모델이 미리 알고 판단한 것은 아니다. 병합 실행은 모든 필수 검사 통과 전까지 잠정 결과로 취급한다. 앞 결과가 바뀌면 이에 의존하는 병합 결과도 무효화한다.

독립 검토가 필요한 단계는 같은 호출의 ‘스스로 점검’으로 대체하지 않는다. 별도 호출도 같은 모델이면 오류가 상관될 수 있으므로 근거와 도구 검증을 함께 사용한다.

표준 평가 업무의 예시 호출 구성은 다음과 같다.

|호출|논리적 단계|호출 후 코드 처리|
|---|---|---|
|A|S1 목적 + S2 기본 사실|모호성·필수 정보·출처 구조 확인|
|B|S3 평가 기준|기준 구조·목적 연결 검사, 필요한 의미 검토 수행|
|C|S4 기준별 판단|누락·참조·계산·규칙 검사|
|D|S5 종합 결론|S6의 코드·Z3 검사와 필요한 의미 검토|
|E|S7 답변|조건·수치·상태 유지 검사|

이 예시는 기본 5회이며 의미 검토·조회 후 재판단·복구가 필요하면 증가한다. 의미 검토가 요구되는 경우 그 호출을 숨겨서 5회로 집계하지 않는다. 코드로 결론을 계산하거나 템플릿으로 답할 수 있는 업무는 D 또는 E를 줄일 수 있다. 모든 업무를 한두 번 호출로 처리한다는 목표를 강제하지 않는다.

동적 절차 생성은 최초 요청 해석과 한 호출에 묶을 수 있다. 다만 생성 절차에 의존하는 실제 판단은 실행 전 검사가 끝난 후 수행한다. 실행 전 목적 적합성 검토는 생성 호출의 자기평가로 대체하지 않는다. 등록된 절차를 변경 없이 재사용하는 경우에는 버전·요청 적합성을 확인하고 불필요한 전체 재생성을 생략한다.

## 11. 최종 답변과 완료 기준

최종 답변은 사용자의 질문에 직접 답하고, 필요한 이유·조건·미확인 사항·출처를 제공한다. 내부 단계 로그 전체를 사용자에게 출력하지 않는다.

핵심 판정·수치·날짜·필수 조건은 구조화된 결과 또는 템플릿으로 유지한다. LLM은 표현을 보완할 수 있으나 새 사실이나 기준을 넣어 결론을 바꾸지 않는다. 새 판단이 필요하면 관련 단계로 되돌린다.

표시 범위는 다음처럼 구분한다.

- 절차상 완료: 정의된 단계와 필수 검사를 수행했다.
- 근거 기반 판단: 확보한 근거에 따라 LLM 또는 업무 규칙이 판단했다.
- 전제하 논리 확인: 명시된 전제에서 결론의 귀결을 확인했다.
- 제약 충족 확인: 입력한 조건을 만족하는 해를 찾았다.
- 조건부·미확정·검증 미완료: 남은 가정이나 미완료 검사가 있다.

전체 답변에 일괄적으로 ‘증명됨’을 붙이지 않는다. 의미 평가와 형식 검증의 범위를 주장별로 관리한다.

완료 조건은 사용자 요구의 필수 부분이 처리되고, 필요한 검사가 수행됐으며, 남은 불확실성이 숨겨지지 않은 상태다. 형식만 충족한 빈 답변은 완료로 처리하지 않는다. 부분 답변으로 종료할 때에는 미해결 항목과 필요한 추가 정보를 남긴다.

## 12. 토큰과 지연 관리

전체 설계서를 매번 프롬프트에 넣지 않는다. 해당 단계의 목적·출력 계약·관련 사실·필요 규칙만 전달한다. 원문은 보존하고 필요한 위치를 참조하며, 요약을 사용하더라도 예외·부정·단위·사용자 제약이 사라지지 않게 한다.

반복 의도 샘플링, 매 요청 전체 규칙 재작성, 같은 판단의 무조건적 다수결, 전체 답변의 반복 검토는 기본 경로에서 제외한다. 위험과 오류 유형에 맞는 필요한 검사만 수행한다.

절차·규칙·프롬프트·사실 버전이 유효하면 이전 결과를 재사용한다. 입력이나 목적이 바뀌면 의존 결과를 무효화한다. 코드 검사와 Z3 연산은 LLM 토큰을 직접 소비하지 않지만, LLM이 도구 호출을 생성하거나 결과를 다시 읽으면 해당 토큰이 발생한다.

### 12.1 산정 방법

요청당 총토큰은 모든 호출의 입력·생성 토큰과 관련 재시도를 포함한다. 별도 보고되는 추론 토큰이 출력 합계에 포함됐는지 확인해 중복 합산하지 않는다. 조회·요약·의미 검사 호출도 포함하고, 초기 절차·규칙 제작 비용은 별도 기록한다.

현재 요청을 위해 즉석 생성한 절차의 생성·검토·수정 토큰은 해당 요청의 운영 비용에 포함한다. 여러 업무에 공통으로 사용할 절차를 별도 개발하는 비용만 초기 제작 비용으로 분리한다. 재사용·수정·신규 생성 경로별 호출·실패·재작업·총토큰을 따로 집계한다.

기존 추론 모델의 사용량은 입력 + 최종 출력 + 추가 추론 토큰으로 비교할 수 있다. 실제 API 집계 방식이 다르면 그에 맞춰 환산한다. 토큰 수, 청구 금액, 이용한도 소모량은 같은 지표로 취급하지 않는다.

### 12.2 가정에 따른 예시

아래 숫자는 실측·예측이 아닌 계산 예시다. 동일 업무를 비교하되 실제 품질 동등성은 별도 평가한다. 입력에는 단계 지시와 스키마를 포함했다고 가정한다.

|구성|입력|출력·생성|합계|
|---|---:|---:|---:|
|외부 절차 A: 목적·사실|2,200|300|2,500|
|외부 절차 B: 기준|1,000|250|1,250|
|외부 절차 C: 기준별 판단|1,400|500|1,900|
|외부 절차 D: 종합 결론|900|200|1,100|
|외부 절차 E: 최종 답변|1,000|600|1,600|
|5회 합계|6,500|1,850|8,350|

기존 추론 모드가 입력 2,500, 최종 출력 600, 별도 추론 3,000토큰을 쓴다고 가정하면 총 6,100토큰이다. 위 외부 절차는 약 36.9% 더 사용한다. 반대로 기존 추론이 6,000토큰이면 총 9,100토큰이므로 위 예시는 약 8.2% 적게 사용한다.

추가 의미 검사·질문·복구가 발생하면 외부 절차의 사용량이 증가한다. 따라서 단계 통제가 자동으로 토큰 절감을 의미하지 않는다. 우선 품질과 통제 효과를 측정하고, 불필요한 호출과 재작업을 줄이는 순서로 최적화한다.

위 8,350토큰 예시는 기존 절차의 실행 비용이며 신규 절차 생성 비용은 포함하지 않았다. 예를 들어 생성에 입력 1,500·출력 500, 실행 전 검토에 입력 1,000·출력 200토큰을 별도로 사용한다고 가정하면 3,200토큰이 추가돼 11,550토큰이 된다. 이 역시 실측값이 아니다. 첫 요청과 재사용 요청의 비용을 구분하고, 절차 정의 전체를 매 단계에 반복 전달하지 않는다.

## 13. 통합 동작 예시

가상의 요청: “보고서 검토를 자동화하려고 하는데 이 방법이 적합한가요? 내부망에서 사용하고 근거 문장을 보여줘야 합니다.”

|단계|예시 산출물|제어 동작|
|---|---|---|
|S1|목적: 보고서 검토 지원. 제약: 내부망, 근거 제시|검토 대상 방법이 없으면 그 정보부터 요청|
|S2|제안서에는 외부 API 사용이 명시됨. 내부망 대체 기능은 미확인|명시 사실과 미확인을 구분해 저장|
|S3|필수: 내부망 실행·근거 추적. 선호: 처리 속도|사용자 필수 조건이 기준에서 빠지면 차단|
|S4|현재 외부 API 구성은 내부망 조건 불충족. 근거 추적은 미확인|미확인을 충족으로 처리하지 않음|
|S5|현재 구성으로는 필수 조건 미충족. 내부 실행 구조와 근거 추적 기능 확인 필요|속도 장점이 필수 조건 위반을 상쇄하지 못하게 함|
|S6|사실·기준·결론 연결 점검|‘내부 실행 불가’를 방법 전체의 영구적 불가능으로 확대하면 수정|
|S7|현 구성의 부적합 이유와 변경·확인 조건을 설명|원문보다 강한 표현과 조건 누락 확인|

사용자가 “실제로는 로컬 모델도 지원한다”는 새 근거를 제공하면 S2를 갱신하고 관련 S4~S7을 재검토한다. 목표와 평가 기준이 그대로라면 S1·S3을 무조건 다시 호출하지 않는다. 일반 코드만으로 충분하면 이 예시에 Z3를 추가할 필요는 없다.

### 13.1 미등록 요청의 즉시 처리 예시

요청: “두 보고서의 결론이 다른 이유를 분석하고 어느 조건에서 각각 맞는지 설명해 주세요.” 등록된 절차가 맞지 않는다면 다음과 같이 동적으로 구성할 수 있다.

|동적 단계|질문과 산출물|필수 확인|
|---|---|---|
|D1 대상 확인|문서·버전·비교할 결론은 무엇인가?|대상 누락과 버전 혼동|
|D2 주장·근거 추출|각 문서의 주장과 근거 위치는 어디인가?|원문 연결과 미확인 유지|
|D3 비교 범위 정리|용어·시점·대상·가정은 어떻게 다른가?|같은 지표를 비교하는지|
|D4 차이 분석|범위 차이인가, 사실 충돌인가, 추론 차이인가?|근거 없는 인과 단정 방지|
|D5 조건별 판단|어느 조건에서 각 결론이 지지되는가?|사용자 요구의 조건별 설명 포함|
|D6 답변|차이·적용 조건·미해결을 어떻게 전달할 것인가?|원문보다 강한 결론을 만들지 않음|

생성기가 D5를 빠뜨렸다면 목적 적합성 검토에서 ‘각각 맞는 조건’이라는 요구가 누락됐음을 지적하고 수정한다. 구조·목적 검사를 통과하면 D1부터 바로 실행한다. 실행 결과는 기록하지만 한 번 성공했다고 표준 절차로 자동 승격하지 않는다.

## 14. 구현 순서와 인수 기준

### 14.1 첫 구현 범위

첫 업무는 ‘방법 평가’로 잡아 단계별 판단 통제를 먼저 확인한다. 형식 검증 기능은 별도의 작은 규칙 판단 사례로 함께 확인한다. 이를 통해 본 시스템을 규칙 엔진에만 한정하지 않는다.

동적 절차 생성·검사·즉시 실행도 이번 구현의 필수 범위에 포함한다. 이미 구현된 v3.0 에이전트는 절차 정의 형식과 검사기, 요청별 실행 허용 상태부터 추가하고 기존 실행 엔진을 재사용한다.

|순서|구현 항목|확인할 결과|
|---|---|---|
|1|절차 레지스트리·단계 계약·실행 상태|선행 단계와 검사 조건 없이 진행하지 않음|
|2|비추론 LLM 호출·구조화 출력·사실 저장|설정 지원 여부를 기록하고 단계별 결과를 구분|
|3|방법 평가 S1~S7·코드 검사|목표에서 기준·판단·결론으로 연결되는지 확인|
|4|의존 관계·복귀·재개|변경된 정보에 의존하는 결과만 다시 처리|
|5|의미 검사·Z3 선택 적용|검사 종류·보장 범위·미확정 상태를 구분|
|6|호출 병합·결과 재사용·토큰 측정|필수 검사 경계를 유지하면서 비용 비교|
|7|동적 절차 생성·실행 전 검사|미등록 요청도 검사 후 등록 대기 없이 즉시 수행|
|8|실행 중 절차 변경·버전 전환|영향 결과 무효화, 이전 실행 결과 혼입·외부 작업 중복 방지|
|9|재사용 후보 평가·등록|평가 기준을 통과한 절차를 적용 범위와 함께 재사용 등록|

구조화된 절차 정의의 동적 생성은 필수 기능이다. 반복 후보 탐색, 여러 완성 답변의 투표, 실행 엔진 자체의 자율 코드 변경, 복잡한 학습 기반 라우터는 초기 필수 범위가 아니다.

### 14.2 필수 시험

필수 기준 누락, 근거 없는 판단, 미확인의 참 승격, 사용자 목적 변경, 사실 버전 변경, 상충 자료, 잘못된 절차 선택, 부정·예외 오역, 모순 전제, 솔버 unknown, 결론의 조건 누락, 반복 복구, 예산 초과, 중단 후 재개를 포함한다.

형식 검사와 의미 검사를 구분해 기록하는지 확인한다. Z3 조건식은 문자열 일치 대신 공통 변수·범위에서 의미 차이가 발생하는 입력이 있는지 비교할 수 있다. 검사 자체가 unknown이면 동치로 판정하지 않는다.

동적 절차의 추가 인수 시험은 다음과 같다.

- 등록되지 않은 업무가 절차 생성·검사를 거쳐 같은 요청 안에서 실행되는가?
- 존재하지 않는 입력 참조, 분기에서 생성되지 않은 값, 무제한 순환을 차단하는가?
- 구조는 맞지만 사용자 요구를 누락한 절차를 목적 적합성 검토에서 찾아내는가?
- 생성기가 필수 검사·도구 범위·실행 예산을 임의로 완화할 수 없는가?
- 변경한 절차가 이전 버전의 실행 허용을 재사용하지 않는가?
- 실행 중 절차 변경 후 영향 결과만 재계산하고 이전 버전의 늦은 결과를 반영하지 않는가?
- 절차 생성·검토 실패 시 무조건 실행하지 않고 유효한 대체·질문·부분 결과로 종료하는가?
- 단일 요청 성공을 반복 사용의 품질 증명으로 취급하지 않는가?

### 14.3 효과 평가

|비교군|목적|
|---|---|
|기존 모델 thinking 켜기|현재 품질·비용 기준|
|같은 모델 thinking 끄기|내부 추론 비활성화의 영향|
|thinking 끄기 + 한 번의 단계 지시 프롬프트|단계 이름을 알려주는 효과|
|thinking 끄기 + 코드 단계 통제|실제 검사 경계·상태 관리의 추가 효과|
|위 구성 + 선택적 Z3|형식 논리 검사의 추가 효과|

같은 업무·자료·최종 요구사항을 사용하고, 품질 우선 조건과 동일 예산 조건을 구분한다. 모델 버전과 추론 설정을 기록한다. 비추론 모드를 지원하지 않는 환경은 별도 조건으로 표시한다.

지표는 업무 정답률, 요구사항 충족률, 근거 없는 주장, 필수 단계·기준 누락, 잘못된 검증 표시, 미해결 비율, 재작업 횟수, 전체 토큰, 처리 시간이다. 실패·보류와 후속 질문 비용을 같은 업무 ID로 묶는다. 설계 조정용 사례와 최종 평가 사례를 분리한다.

성능 도입 기준은 업무별로 사전에 정한다. 정답률뿐 아니라 미해결 비율과 비용까지 허용 범위에 들어가는지 확인한 뒤 해당 업무에서 내부 추론 대체가 가능하다고 판단한다. 전체 도메인에 대한 완전 대체를 일괄 선언하지 않는다.

동적 기능은 기존 절차만 사용하는 구성과 추가 비교한다. 절차 레지스트리를 고정한 뒤 미등록 업무 평가 세트를 별도로 구성하고, 잘못된 실행 허용·불필요한 거절·목적 누락·생성 비용을 측정한다. 해당 평가 세트의 답을 반영해 절차를 등록한 다음 같은 문제를 ‘새 업무’ 성능으로 다시 보고하지 않는다. 재사용 승격 평가에도 별도의 사례를 사용한다.

## 15. 구현자가 지켜야 할 핵심 사항

1. 시스템의 중심은 코드가 실행 규칙을 통제하는 단계별 사고 절차다. 절차 정의는 미리 등록하거나 동적으로 생성할 수 있다.
2. LLM은 각 단계의 의미 판단을 담당하고 코드는 흐름과 계약을 통제한다.
3. 목표·사실·기준·판단·결론을 식별 가능하게 연결한다.
4. 검사 통과와 사실의 진실성, 형식적 증명을 구분한다.
5. 미확인과 가정은 후속 단계와 최종 답변까지 유지한다.
6. 오류는 관련 단계에서 수정하고 의존 결과를 무효화한다.
7. 병합 호출이 중간의 필수 검사 경계를 우회하지 않게 한다.
8. Z3는 필요한 논리 부분에만 사용하며 sat을 결론 증명으로 해석하지 않는다.
9. 모델의 추론 설정과 실제 호출·토큰을 기록한다.
10. 품질 향상, 내부 추론 대체, 토큰 절감을 각각 측정한다.
11. 미등록 절차도 구조·목적·실행 조건 검사를 통과하면 현재 요청에서 바로 실행한다.
12. 요청별 실행 허용과 검증된 재사용 등록을 구분하고 절차 변경은 새 버전으로 관리한다.

## 16. 참고 근거와 적용 범위

이 문서는 합의한 시스템 구조에 대한 설계 제안이다. 다음 자료는 도구 실행과 형식 검증의 원리를 뒷받침하며, 이 통합 설계의 성능을 입증하는 실험 결과는 아니다.

- [Microsoft Z3 Guide — Propositional Logic](https://microsoft.github.io/z3guide/docs/logic/propositional-logic/): 만족 가능성과 타당성, 부정식의 불만족성을 통한 검증.
- [Microsoft Z3 Guide — Advanced Topics](https://microsoft.github.io/z3guide/programming/Z3%20Python/advanced/): unsat core와 최소성의 한계.
- [Logic-LM](https://aclanthology.org/2023.findings-emnlp.248/): 자연어 형식화와 기호 솔버의 역할 분담.
- [PAL: Program-aided Language Models](https://arxiv.org/abs/2211.10435): LLM의 표현 생성과 외부 프로그램 실행의 분담.
- [Oxford OATML — Semantic Entropy](https://oatml.cs.ox.ac.uk/blog/2024/06/19/detecting_hallucinations_2024.html): 반복 생성의 의미 분포와 체계적 오류 탐지의 한계.
