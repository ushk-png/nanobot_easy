# 실전 스킬 작성 가이드 — 성능을 좌우하는 것들

전제: 스킬의 성능은 두 지점에서 결정된다.
1. **검색/선택 단계**: description이 질문과 매칭되는가 → 스킬이 선택되느냐의 문제
2. **실행 단계**: 본문이 LLM의 행동을 실제로 바꾸는가 → 답변 품질의 문제

대부분의 스킬 실패는 (1)에서 일어난다. 아무리 본문이 좋아도 선택되지 않으면 존재하지 않는 것과 같다. 그래서 이 가이드는 description에 절반을 쓴다.

---

## 1. Description 작성 — 라우팅 정확도의 전부

### 1.1 사용자의 실제 발화를 넣어라 (가장 효과 큰 기법)

LLM과 벡터 검색 모두 "설명"이 아니라 "표현의 유사성"으로 매칭한다.
개념어로 쓰지 말고 사용자가 실제로 치는 문장을 넣어라.

나쁨 (개념 설명):
```yaml
description: 비교 분석형 질문에 대한 답변 방법론
```

좋음 (트리거 발화 나열):
```yaml
description: >
  두 개 이상의 대상을 견주는 질문에 사용. 트리거 예:
  "A랑 B 중에 뭐가 나아?", "차이가 뭐야", "vs", "장단점 비교해줘",
  "어떤 걸 선택해야 해?". 단일 대상의 장단점만 묻는 질문에는 사용하지 않음.
```

규칙:
- 트리거 발화 3~7개. 실제 로그에서 가져온 문장이 지어낸 문장보다 항상 낫다.
- 동의어 변형 포함 (비교/차이/vs/뭐가 나아 — 사용자마다 쓰는 말이 다르다)
- 한국어 서비스면 한국어 발화로. 영어 스킬을 번역만 하면 매칭이 깨진다.

### 1.2 when_NOT_to_use를 반드시 써라

스킬이 늘수록 문제는 "선택 안 됨"이 아니라 "잘못 선택됨"으로 바뀐다.
경계가 헷갈리는 이웃 스킬을 지목해서 밀어내라.

```yaml
when_not_to_use:
  - 단계별 방법을 묻는 질문 (→ answer-howto 사용)
  - 원인을 묻는 질문 "왜 안 되지?" (→ answer-diagnosis 사용)
```

이웃 스킬 이름을 직접 언급하는 것이 핵심이다. LLM이 후보 간 경합에서 판단할 근거가 된다.

### 1.3 오답 사례를 description에 역주입하는 루프

운영에서 잘못 라우팅된 실제 사례가 최고의 학습 데이터다.
"X라는 질문에 이 스킬이 잘못 선택됐다" → 그 X를 when_not_to_use에 그대로 추가.
"Y라는 질문에 선택됐어야 했다" → Y를 트리거 예에 추가.
이 루프를 주 1회만 돌려도 라우팅 정확도가 계속 오른다. 코드 수정 없이.

## 2. 본문 작성 — LLM의 행동을 실제로 바꾸는 법

### 2.1 형용사 대신 절차와 형식

LLM은 "정확하게", "친절하게", "전문적으로" 같은 형용사로는 행동이 거의 안 바뀐다.
바뀌는 것은 (a) 순서가 있는 절차, (b) 출력 형식 템플릿, (c) 예시다.

나쁨:
```
비교 질문에는 공정하고 균형 잡힌 답변을 하세요.
```

좋음:
```
## 절차
1. 비교 대상과 사용자의 판단 기준을 질문에서 추출한다. 기준이 없으면
   해당 도메인의 표준 기준 3개를 스스로 정한다 (예: 가격/성능/유지보수).
2. 기준별로 두 대상을 대조한다. 한쪽 정보가 없으면 "확인 안 됨"으로 표기하고
   지어내지 않는다.
3. 마지막에 "이런 경우엔 A, 저런 경우엔 B" 형태의 조건부 결론을 1문장으로 낸다.
   무조건적 승자 선언은 하지 않는다.

## 출력 형식
| 기준 | A | B |
|---|---|---|
(표 다음에 조건부 결론 1~2문장. 그 외 서론·부연 금지)
```

### 2.2 좋은 예시 1개 + 나쁜 예시 1개 (few-shot의 실전 최소형)

예시는 지시문 10줄보다 강하다. 특히 **나쁜 예시와 그 이유**가 효과가 크다 —
LLM이 저지르는 전형적 실수를 미리 보여주고 금지하는 것이기 때문.

```
## 예시
질문: "PostgreSQL이랑 MySQL 중 뭐 써야 해?"

좋은 답변: (표 + "복잡한 쿼리와 확장이 중요하면 PostgreSQL,
단순 CRUD 위주의 검증된 운영이 중요하면 MySQL")

나쁜 답변: "PostgreSQL이 더 좋습니다. 기능이 많기 때문입니다."
→ 이유: 사용자 상황을 묻지도 반영하지도 않은 무조건 결론. 금지.
```

예시는 각 1개면 충분하다. 3개 이상 넣으면 토큰만 먹고 효과는 포화된다.

### 2.3 실패 지침을 반드시 포함하라 (에이전트 스킬의 차별점)

정적 문서와 에이전트 스킬의 차이가 여기다. 절차가 막혔을 때의 행동을 정의하라.
이게 없으면 서브에이전트가 멈추거나 지어낸다.

```
## 실패 시
- 검색 결과가 비면: 쿼리를 더 짧게 바꿔 1회 재시도. 그래도 없으면
  "찾지 못함"을 명시하고 아는 범위만 답한다. 추측으로 채우지 않는다.
- 입력 파일이 형식에 안 맞으면: 어느 부분이 안 맞는지 보고하고 중단한다.
  임의로 형식을 고치지 않는다.
```

(v2 설계의 "Subagent는 국지적 판단만" 원칙이 스킬 문서에서 구현되는 지점이 바로 이 섹션이다.)

### 2.4 금지 목록은 3~5개로 짧게, 이유와 함께

금지가 10개 넘으면 LLM이 다 지키지 못하고, 이유 없는 금지는 잘 무시된다.
"~하지 마라 (왜냐하면 ~)" 형태로 가장 자주 터지는 것만.

### 2.5 분량: 본문 30~150줄

- 30줄 미만: 절차·형식·예시·실패지침 중 뭔가 빠진 것. 행동이 안 바뀐다.
- 150줄 초과: 컨텍스트를 오염시키고 핵심 지시가 묻힌다. 쪼개거나(스킬 분리)
  참조 파일로 빼라(SKILL.md는 요약+절차, 상세 표는 같은 폴더의 별도 파일로 두고
  "필요하면 read_file로 reference.md를 읽어라"라고 지시 — progressive disclosure).

## 3. 표준 템플릿

```markdown
---
name: answer-comparison
description: >
  [한 줄 정의]. 트리거 예: "발화1", "발화2", "발화3".
  [경계 조건]에는 사용하지 않음 (→ 이웃스킬명).
metadata: {"nanobot": {"domain": "qa", "risk_level": "low"}}
---

# [스킬 이름]

## 언제 쓰는가
- 트리거 발화 예시 (description과 동기화)
## 언제 쓰지 않는가
- 이웃 스킬 지목

## 절차
1. ~
2. ~
3. ~

## 출력 형식
(템플릿 그대로 제시)

## 예시
좋은 답변 1개 / 나쁜 답변 1개 + 이유

## 실패 시
- 상황별 행동 정의 (재시도 규칙, 보고 후 중단, 추측 금지)

## 금지 (3~5개, 이유 포함)
```

## 4. 테스트 — 쓰고 나서 해야 성능이 된다

### 4.1 라우팅 테스트 (스킬 등록 전 필수)
실제 질문 10개(이 스킬이 선택돼야 하는 5개 + 이웃 스킬로 가야 하는 5개)를 만들어
스킬 선택이 맞는지 확인. 오답이면 코드가 아니라 description을 고친다.
v2 설계의 Skill Tester가 자동화할 대상이 바로 이것이다.

### 4.2 A/B 실행 테스트
같은 질문을 스킬 있음/없음으로 각각 실행해서 답변을 비교.
차이가 안 보이면 그 스킬 본문은 형용사 덩어리라는 뜻 — 2.1로 돌아가라.

### 4.3 운영 지표와 연결
success_count/failure_count(검증 게이트 통과율)를 스킬별로 적재하고,
실패율 상위 스킬부터 본문을 개선한다. 감이 아니라 데이터로 고친다.

## 5. 자주 하는 실수 (안티패턴)

| 안티패턴 | 증상 | 처방 |
|---|---|---|
| 백과사전형 | 도메인 지식을 잔뜩 서술, 절차 없음 | LLM이 이미 아는 지식은 빼고 "어떻게 답할지"만 남긴다 |
| 형용사형 | "정확하고 친절하게" | 절차+형식+예시로 교체 |
| 만능형 | 하나의 스킬이 5가지 질문 유형 커버 | 라우팅이 애매해짐. 유형당 1스킬로 분리 |
| 과분할형 | 거의 같은 스킬 12개 | 선택 경합으로 정확도 하락. when_not_to_use로 통합 정리 |
| 영어 직역형 | 외부 스킬 번역만 해서 등록 | 트리거 발화를 한국어 실사용 표현으로 재작성 |
| 고아형 | 등록 후 방치 | 오답 역주입 루프(1.3)에 편입, 실패율 모니터링 |

---

## 6. 우선순위 요약

효과 대비 노력 순으로:
1. description에 실제 사용자 발화 트리거 넣기 (1.1) — 최대 효과
2. when_not_to_use로 이웃 스킬 밀어내기 (1.2)
3. 출력 형식 템플릿 명시 (2.1)
4. 나쁜 예시 + 이유 1개 (2.2)
5. 실패 지침 (2.3)
6. 오답 역주입 운영 루프 (1.3, 4.3) — 장기적으로 가장 큰 효과
