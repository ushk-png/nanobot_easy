# 의도·정보 요구 기반 컨텍스트 선택: 구현 및 검증 보고

이 기능은 **기본 비활성화**인 실험 경로다. 운영 설정은 변경하지 않았으며,
서비스 재시작·유료 LLM 호출·실제 모델 간 비교 실험은 수행하지 않았다.
토큰 상한을 맞추기 위해 필수 근거를 버리지 않는다. 안전하게 선택할 수 없으면
관련 원문 구간을 복원하고, 실제 입력 한도를 넘으면 분할 또는 한도 확장을 요청한다.

감사에서 발견한 11개 결함의 수정 경계와 최신 로컬 검증은
[감사 결함 수정 기록](design/context-selection-repair.md)을 기준으로 한다.

## 현재 구현 확인과 진단 차이

- `_state_build()`는 기존 경로에서 `session.get_history()`를 호출한다.
- `Session.get_history()`는 미통합 이력을 선택한다. 기본 상한은 2,000개이며 주제 필터는 없다.
  다만 현재 코드는 `context_window_tokens`에서 메시지 상한을 계산하고,
  `_replay_token_budget()` 및 실행 직전 `ContextGovernor`의 토큰 제한도 적용한다.
  따라서 **현재 제한이 약 47만 토큰에서만 작동한다는 진단은 맞지 않는다**.
  정확한 한도는 모델 컨텍스트·출력 예약·안전 여유·`contextBlockLimit` 설정에 의존한다.
- `conversation_focus`는 최근 대화에서 만든 검색 보조 메타데이터다. 확정 작업 상태로 쓰지 않는다.
- 기존 `search_memory`는 모델의 도구 호출로 실행되며 기존 재생 이력을 대체하지 않는다.
- `MemorySearcher.search()`의 FTS5/청크/엔티티 검색, 주변 구간·도구 쌍 복원,
  이벤트 제외 및 기본 4,000토큰 검색 예산이 이미 존재한다.
  검색 예산은 최종 실행 입력에서 원문을 버리는 상한으로 사용하지 않는다.
- 원본 `RawEvent`에 이벤트·세션·시퀀스·부모 참조가 있고,
  메타데이터에 `tool_calls`와 `tool_call_id`가 있다.
- 기존 `tasks`는 6개 기본 열만 있고 `state_store.py`는 향후 투영을 위한 자리였다.
  이 작업 전에는 실제 작업 상태 갱신에 사용되지 않았다.
- 제공자 공통 인터페이스에는 `response_format` 인자가 없다.
  OpenAI Chat/Responses/Codex와 Anthropic 구현은 기존 도구 스키마 변환 경로를 제공한다.
  이를 이용한 **변경을 수행하지 않는 `submit_context_design` 함수 스키마**를 사용한다.
  서버의 strict JSON 출력을 모든 제공자에서 가정하지 않는다. 반환된 함수 인자 또는
  JSON 본문을 Pydantic으로 검증한 뒤 별도의 의미 검증을 수행한다.

이전 응답 ID, 서버 대화 유지, 캐시 최적화, 새로운 다중 주제 분류 서비스는 추가하지 않았다.

새 경로는 `get_history()`를 다시 뒤에 붙이지 않는다. 기존 경로는 기본값으로 유지한다.

## 설정과 복구

기존 설정의 `agents.defaults`에 다음 설정을 사용할 수 있다. **이번 작업에서는 적용하지 않았다.**

```json
{
  "contextSelection": {
    "enabled": false,
    "failureMode": "block",
    "recentMessages": 8,
    "searchTokens": 4000,
    "designMaxTokens": 3000,
    "designTimeoutSeconds": 90,
    "executionTargetTokens": 16000
  }
}
```

- `enabled: false`: 설계 호출 없이 기존 경로. 되돌릴 때 이 값을 사용한다.
- `enabled: true`: 사용자 요청당 설계 1회가 기본이다. 형식/의미 오류는 1회만 복구한다.
  제공자의 기존 일시적 오류 재시도는 별도로 유지하며 각 시도를 계측한다.
- `failureMode: block`: 설계 검증 실패 시 실행 중단. 기본값이다.
- `failureMode: legacy`: 입력 선택 단계에서 실패하면 사유를 기록하고 기존 도구 루프로 복구한다.
  설계 실패 호출과 복구 실행 호출을 같은 요청의 누적 사용량으로 집계한다.
  실행 중 용량 초과는 자동 전체 이력 재생으로 바꾸지 않고 중단한다.
- 비활성화하거나 복구하더라도 원본 및 추가 투영 테이블을 삭제할 필요는 없다.
- 실험 경로에서는 기존 per-turn 이력 통합 LLM을 자동 호출하지 않는다.
  기본 비활성 경로의 통합 동작은 유지한다.

별도 shadow/live 비교 모드는 자동 실행하지 않는다. 오프라인 비교 도구에는 실제 API
호출 경로가 없고, 모의 제공자를 사용한다.

## 처리 흐름과 최소 입력 예시

사용자 원문 저장 → 제한된 최근 대화·작업 상태·참조 후보·기능 카드 구성 →
설계 호출 → 스키마 검증 → 의미 검증 → 코드의 메모리 검색·원문 복원 →
선택한 스킬/도구를 포함한 실행 입력 → 기존 실행 도구 루프 → 관측 및 완료 상태 기록.

최소 입력은 다음 구조다. 실제 생성한 전체 예시는 인접한 JSON 파일에 있다.

```json
{
  "request": "2+2?",
  "media_present": false,
  "task_state_status": "missing",
  "task_state": null,
  "task_candidates": [],
  "references": {},
  "sources": [],
  "capabilities": [{"name": "read_file", "description": "Read local files using the existing workspace permission checks"}],
  "material_refs": [],
  "known_material_clues": []
}
```

실제 모의 설계 출력:

```json
{
  "goal": "Answer the self-contained arithmetic question",
  "request_type": "explain",
  "task_relation": "new",
  "task_id": null,
  "route": "direct",
  "constraints": [],
  "information_needs": [],
  "capabilities_needed": [],
  "completion_checks": ["Return 4"],
  "unresolved": [],
  "answer": "4"
}
```

`information_needs`의 스키마는 `id`, `required`, `question`, `source_kind`, `scope`,
`query`, `source_ids`, `acceptance`를 필수로 한다. 전체 JSON Schema는
`DESIGN_SCHEMA = IntentDesign.model_json_schema()`로 코드에서 생성한다.

첫 호출에 전체 세션·장기 기억·상시 스킬 본문·전체 도구 정의·과거 도구 결과를 자동 첨부하지 않는다.
공통 규칙/워크스페이스 지침은 유지한다. 기능 이름과 짧은 설명,
원문 이벤트 ID, 작업 출처·워터마크, 명시적인 사용자 제약 후보를 제공한다.
Q 목록, 제외할 제안, 미완료 작업, 이전 설정은 후보 또는 미해결로 표시한다.
최근 범위 밖의 명시적인 사용자 제약도 실제 원문 발췌와 출처를 제공한다.
작업 투영이 없으면 `missing`, 부분적이거나 최신 반영을 확신할 수 없으면 `stale`이다.

미등록 기능·없는 출처·입력에 없는 파일 단서를 거부한다. 제약은 사용자 출처의 원문 인용만
허용한다. 사용자 승인을 만들어낸 목표와 명시적 금지에 대한 대표적인 충돌을 검사한다.
자연어 제약을 완벽히 판정하는 별도 의미 검증기가 있는 것은 아니다. 이러한 검사 외에도
실행 입력의 사용자 원문과 실제 도구 권한 검사를 그대로 유지한다.

## 검색, 상태, 동시성

- 자동 검색에는 추가 모델 도구 호출을 요구하지 않는다. 알려진 원문 참조와 작업의 사용자
  원문을 우선 사용하고, 검색 결과를 현재 작업/세션 순으로 정렬한다. 검색 범위는 런타임의
  owner/workspace/agent 범위를 넘지 않는다.
- `conversation_focus`로 결과를 강제 제외하지 않는다. 현재 경로는 정확성을 위해
  작업 참조와 원문을 우선하며 focus 값을 반드시 쓸 필요는 없다.
- 검색된 세션의 후속 사용자 원문을 함께 복원해 변경·취소를 놓치지 않도록 한다.
  검색기의 무일치 시 recency fallback을 그대로 근거 확보 성공으로 취급하지 않는다.
- 검색 예산 이후에는 관련 원문을 잘라 읽지 않는다. 조회 오류 시 최근 관련 원문 구간부터
  복원한다. 조회 실패와 “과거 결정 없음”을 구분한다.
- 기존 세션의 부분 상태는 보수적으로 사용자 원문을 더 복원한다. 이는 일시적으로 많은
  사용자 원문을 포함할 수 있다. 선택성을 높이기 위해 제약을 임의로 제거하지 않았다.
- 기존 `tasks` 열을 변경하지 않고 `task_context_versions`, `context_selection_runs`를
  `CREATE TABLE IF NOT EXISTS`로 추가한다. 새 경로를 처음 사용할 때 수행되는
  비파괴·반복 가능한 마이그레이션이며 기존 이벤트를 수정·삭제하지 않는다.
- 상태는 목표/완료 조건, 원문 제약, 모델 제안, 사용자 결정 원문, 미완료/차단,
  도구 관측/검증 근거, 출처, 대체·취소 후보, 버전, 마지막 반영 이벤트를 보유한다.
  의미가 불확실한 “그 방식”의 대체 관계는 확정하지 않는다.
- `BEGIN IMMEDIATE` 및 기대 버전 검사로 오래된 작성자의 덮어쓰기를 거부한다.
  세션당 여러 작업을 저장하고 주제 전환을 이전 작업 완료로 바꾸지 않는다.
- 새 원본에는 안정적인 이벤트 ID와 단조 증가하는 시퀀스를 부여한다.
  같은 외부 메시지 ID/원문 재수신은 중복 실행하지 않는다.
- 재시작 후 투영과 기존 체크포인트를 복원한다. 재개할 작업의 마지막 실행 구간과
  그 호출에 연결된 늦은 결과를 복원하며, 도구 결과가 사용자 결정 워터마크를 앞당기지 않는다.
- 실행 중 새 사용자 지시는 기존 입력 주입 경로로 유지하고 이전 완료 판정을 무효화한다.
  종료 시 새 원문을 투영에 추가하고 재조정 전까지 완료로 처리하지 않는다.

## 실행 루프와 완료 조건

`discover_context_capabilities`로 누락된 등록 도구/스킬을 추가 로딩할 수 있다.
`revise_context_requirements`는 근거 부족·실제 자료 충돌·새 지시가 있을 때만 사용하며,
요구와 완료 조건을 추가한다. 기존 제약이나 필수 요구를 제거하는 권한은 없다.
별도 설계/요약 LLM을 매 도구 결과마다 호출하지 않는다. 내부 연속 실행과 시스템의
하위 작업 결과는 저장된 설계를 재사용하고, 같은 요청의 호출 순번·누적 사용량을 이어간다.
대상이 없거나 여러 작업 중 어느 것인지 불명확하면 새 설계를 추측해 실행하지 않는다.

필수 근거가 미해결이면 `prepare_call()`과 도구 실행 경계에서 변경 도구를 차단한다.
`resolve_context_need`는 실제 성공한 읽기 호출과 자료 종류가 일치해야 한다.
과거 이벤트가 존재한다는 사실만으로 현재 파일을 읽었다고 판정하지 않는다.
기존 파일 상태/경로 권한 검사를 재사용하고, 편집 전 현재 파일 재독을 지시한다.

진행 중 호출과 결과는 연결을 유지한다. 최근 결과와 알 수 없는 비구조화 결과는 보존한다.
내부 생산 경로가 실제 원본 이벤트·자료 버전·내용 해시·요약 범위를 등록한 완료 결과만
오래된 결과부터 줄일 수 있다. 문서/도구 출력 JSON의 `context_summary` 필드는 제어 정보로
해석하지 않는다. 필수 근거로 연결된 원문은 별도로 보존하고, 사실·실패·검증·원문 참조를 남긴다.
현재 기본 도구의 모든 자유 텍스트를 안전하게 요약한다고 주장하지 않는다.
알 수 없는 결과는 소프트 예산을 늘리고, 실제 모델 한도를 넘으면 보존한 채 중단한다.
새 경로는 저장 단계에서 긴 원문 도구 결과를 절단하지 않는다.

실행 완료는 `record_context_completion`으로 각 완료 조건과 실제 성공 도구 호출을 연결해야
지원된다. 수정/실행 요청은 실제 변경 도구 관측도 요구한다. 계획 설명만으로 완료 처리하지 않는다.
명시적인 기록이 없거나 필수 근거가 없으면 `incomplete`로 표시한다.
도구 성공에 기반한 **실행 모델의 완료 평가**와 독립적으로 의미까지 검증된 결과를 구분한다.
`completion_tool_supported`와 `completion_verified`도 구분한다. 후자는 현재 독립적인
실행 의미 검증을 가정하지 않으며, 외부 작업이 없는 직접 답변 경로의 구조적 완료에만 사용한다.

## 계측과 토큰 비교

요청 ID, 작업 ID, design/execute/legacy_fallback 단계, 호출 순번을 제공자의 각 시도에 연결한다.
성공·실패·스트리밍·재시도를 포함한다. 구성 요소별 추정치, 응답에 제공된 사용량,
선택/제외 수, 검색/재설계/복구/충돌/용량 초과 사유, 누적 토큰·시간·완료 조건 수를 저장한다.
`provider_usage_missing_calls`가 있으면 전체 `provider_total_tokens`는 null이며,
확인된 부분만 `known_provider_total_tokens`로 구분한다. 전송 전 시도 저널을 생성하여
응답 없는 실패·취소·타임아웃도 남기고 미확인 사용량을 0으로 확정하지 않는다.
추정치를 제공자 실측으로 대체해 표시하지 않는다.

일반 로그에는 새 경로의 사용자/답변 원문·도구 인자·제공자 오류 원문을 기록하지 않는다.
계측 JSON에는 민감한 원문이나 인증정보를 넣지 않는다. 원문/작업 자료는 기존 범위 제한
저장소에 보존하며 로그와 구분한다.

```bash
PYTHONPATH=. .venv/bin/python scripts/eval_context_selection.py
```

이 합성 사례는 30개 과거 도구 턴 뒤의 독립적인 산술 질문이다.
현재 로컬 추정: 기존 44,721 토큰, 첫 설계 포함 후보 8,623 토큰이다.
약 80.7% 감소한 **한 사례의 추정치**이며 목표치나 합격 기준이 아니다.
첫 설계의 공통 규칙/스키마를 포함하면 2,000~4,000 목표를 넘을 수 있고 이를 잘라내지 않는다.
다른 작업에서는 설계·완료 기록의 추가 비용이나 필수 근거 확장으로 증가할 수 있다.

실제 비교 시 요청별 비용은 다음처럼 합산한다.

- 후보: 모든 설계·복구 호출 + 모든 실행/재시도/추가 검색 후 호출 + 완료 검증 호출의 입출력 토큰.
- 기존: 같은 시작 상태와 도구 결과에서 기존 경로의 모든 호출 입출력 토큰.
- 제공자 input/output/cache/reasoning 사용량을 보존하고, 모델별 실제 단가를 별도로 적용한다.
  입력 길이 추정이나 캐시 적중만으로 비용/성능 보존을 주장하지 않는다.

## 운영 전 최소 실험 절차 — 이번에는 미실행

1. 원본 세션/DB 백업을 복제한 별도 워크스페이스를 사용한다. 실제 서비스 대신 부작용 없는
   도구 대역이나 테스트 저장소를 쓴다. 실행당 비용·최대 호출 수·타임아웃을 먼저 정한다.
2. 14개 요구 사례를 모두 포함하고, 주제 전환·취소·유효 제약·모호한 참조·실패 재시도가
   섞인 소수의 비식별 요청 쌍을 준비한다. 정답/필수 근거/금지 동작/완료 판정을 먼저 고정한다.
3. 같은 모델·설정·초기 상태·기록된 도구 결과에서 기존/후보를 독립 실행한다.
   별도 승인 후에만 제한된 실제 유료 모델 호출을 수행한다. 기본 자동 비교는 하지 않는다.
4. 총 토큰·요청 비용·지연과 함께 최신 제약·참조 대상·미완료 작업·필수 근거·도구 쌍 보존,
   실제 산출물·검증 결과, 잘못된 완료 선언, 불필요한 질문·반복을 사람이 평가한다.
5. 필수 제약 누락/금지 동작/잘못된 완료가 있으면 전환하지 않는다. 작업 종류별 정확도와
   완료율의 차이를 보고, 표본이 작으면 동등성을 주장하지 않는다. 안정성을 확인한 뒤에만
   제한적으로 활성화하고 `enabled: false` 복구를 준비한다.
